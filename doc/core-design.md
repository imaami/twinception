# Daemon core design

Design for the threaded, asynchronous HTTPS core of the daemon, to be built before the semantic engine. Bracketed tags cite measurements and code reviews made while designing it (2026-10-09): [M] mcp2210-proxy's threading, [T] twinception/askai under load, [S] srtview's stalls under load, [P] platform and protocol probes, [ws] a work-sharing simulation, [J1]/[J2] the design judges' re-measurements. The experiments themselves were scratch work and are not in the repository.

## Summary

**Yes: the core can and should be finished before the semantic engine is designed.** The engine needs five things from the core, and none of them depends on the engine's design:
1. a bounded CPU step (`step(task, budget) → DONE | MORE`) with placement;
2. a blocker pool for files and sqlite;
3. supervised git children;
4. an LLM scheduler with classes, fairness, cancellation and progress;
5. a stutter harness.

The core builds all five, and askai's `tools/call` and a synthetic task are their first users. Building the engine first would repeat srtview, where semantic work grew on the thread that serves clients.

**In the core:** N client loops (N = logical cores; from S5, as measured, one fewer, §1) and home, a sidekick loop for the shared services, plus a brainstem (the main thread), a logger and two blocker threads; lock-free per-loop inboxes and generation handles; HTTPS (OpenSSL 3.6) with HTTP/1.1, chunked, SSE, limits and deadlines behind a stream interface; MCP Streamable HTTP in every era askai supports; the LLM scheduler; tasks, git children, timers; `struct buf`; non-blocking logging, metrics, watchdog, shutdown, reload; the load harness gating CI.

**Not in the core:** the semantic archive, search, prompts and schemas; HTTP/2 and the MCP tasks extension (next); WebSockets, io_uring, HTTP/3; kTLS (no CONFIG_TLS here [P]); SSE resumption (removed in 2026-07-28 [P]).

**Why no srtview stutter.** srtview stalled on O(state) work per event on its serving thread (a 3.4 s refold per landing, an O(N) peek per offer), uncoalesced pokes, a mutex held across file I/O, and one non-streamed LLM lane [S]; mcp2210-proxy on lifetime and policy bugs [M]. Here loop work is only bounded steps under a per-turn budget; loops never block, lock, touch files or scan whole state; wakeups coalesce; admission bounds every queue; the LLM stream has an idle timeout and fair queuing. Each step counts its work in units with fixed bounds, and CI fails when a step exceeds one, when a client is starved while others are served, or on errors, lockouts and leaks (§8); latency is reported, and judged only against the same machine's idle baseline.

**Basis.** The judges split 93 to 90. The base is the winner on points, evolve-existing (in-place loop.c/httpd.c, level-triggered, one load-aware acceptor, fd BIO, staged gates). Its four-way-guarded shared job had a use-after-free [J2], so the ownership model comes from symmetric-loops: lock-free inbox, generation handles, one completion per job. Further grafts: a turn that always runs one bulk step, sliced escaping, the EMFILE spare fd, a per-principal connection cap, a separate logger (symmetric); an open-loop probe, nice-0 helpers, task re-placement at slice boundaries, progress as state (work-sharing).

## 1. Thread model

| Thread | Owns | Blocks in |
|---|---|---|
| brainstem (main) | signalfd, process lifecycle (start, shutdown), watchdog, resource monitor; no client work (§11.1) | `ppoll` |
| client loops 1..N | its connections for life (fd, `SSL*`, bufs, parser, call slots, timers), its tasks, the man fetches it began and their children (S6m), its log ring | `epoll_pwait2` |
| home | the listener and placement (S5); LLM scheduler + curl multi, job registry; configuration (S7), `SSL_CTX` (S9); serves no client (§11.1) | `epoll_pwait2` |
| logger ×1 | stderr | `poll`, `writev` |
| blocker ×2 | posted file and DNS closures; from S5 the trim's walk of the arenas (§5) | file syscalls, `getaddrinfo`, `malloc_trim` |

**N** = CPU_COUNT(sched_getaffinity), capped by cgroup `cpu.max`; S5 runs N − 1 client loops beside home, at least 1 and at most 255, the handle's loop field.

**Extra threads** exist only for APIs that can only block, and sleep in the kernel, so runnable threads stay at N. The logger exists because stderr's O_NONBLOCK is shared with the parent (askai froze 115 s in fprintf [T]); the blockers because regular files ignore O_NONBLOCK (two, so a slow fsync never delays a cert reload). The brainstem wakes only for signals, its watchdog's looks (every half threshold, 10 ms by default) and a resource sample a second.

*As built in S3* (N = 1, before home, §11.1): five threads. The brainstem is the main thread; one loop thread (`loop0`) serves the clients and does home's work, the listener and the curl multi included; the logger and two blockers sleep until there is work. Every thread is started with all asynchronous signals blocked and named for `top`. The logger and the blockers are detached: each counts itself out with an atomic and writes the brainstem's eventfd, which therefore stays open until the process exits. The loop thread is joined, so its library state is gone before `exit()` runs OpenSSL's cleanup; a forced exit detaches it instead (review of S3: a finished thread left unjoined at `_exit` is a ThreadSanitizer report). Before it starts any, the brainstem grows the descriptor table to 65 536 (or the limit): once threads share it, the kernel waits for an RCU grace period each time it grows, 7–11 ms per doubling here, in whichever `accept` or `socket` call needed the descriptor; the first S3 campaign saw these as steps of up to 15.5 ms. The table costs the kernel 512 KiB; past 65 536 descriptors each doubling still waits.

*As built in S4* (N = 1, §11.1): six threads. The brainstem starts home (thread `home`, loop 0 of the handles) and then client loop 1 (`loop1`), each through the start handshake with every signal blocked, its own log ring, and its turn under the watchdog; the logger and the blockers as in S3. Home runs a `struct loop` of its own and serves no client: it owns the curl bridge (`http.c`: the multi, its timers on home's heap, host lookups on the blockers into `CURLOPT_RESOLVE`), the registry of jobs in flight and a minimal scheduler: admission, a cap on the jobs in flight (`--max-calls`, 256) beyond which a job ends at once as busy, and first-in first-out starts (§4). Client loop 1 keeps the listener, its connections, httpd, MCP (parsing in slices, replies, SSE) and its call slots. Each loop has its stash and takes part in reliefs; `/metrics` labels their series `loop="1"` and `loop="home"`, and SIGUSR1's lines are home's when they say so. Home is a runnable thread beside the N client loops; it mostly sleeps in `epoll_pwait2` while curl waits on the upstream, and whether S5 runs N or N − 1 client loops beside it is left to S5's measurements.

*As built in S5*: client loops (`loop1`, `loop2` and on) serve the clients, beside home (loop 0 of the handles), the brainstem, the logger and two blockers as in S4. The brainstem allocates the loops' threads, starts home, then each client loop through the start handshake with every signal blocked, and once all run orders home to open its door (§3, §6). Each client loop has its own server (`httpd.c`), MCP (with `mcp_static` shared, immutable), stash, relief and log ring, and its turns are under the watchdog. A loop thread's stack is 1 MiB, as each counts against RLIMIT_DATA, where RLIMIT_STACK's 8 MiB default made 33 threads take 264 MiB. The default N is one fewer than the CPUs askai may use (CPU_COUNT of its affinity, capped by the `cpu.max` quotas of its cgroup and their ancestors, ceil(quota / period), "max" being none), at least 1 and at most 255; `--loops N` sets it, 0 being that default. With one client loop askai serves as S4 did, but that home accepts. **N or N − 1** (doc/core-measurements.md, S5): askai on 16 CPUs (8 cores with their SMT siblings) and on 8 (4 cores), the load on the other 8 cores, three rounds of `storm`, `race` and `check` each. It is a trade, not a free choice. For N: the storm's probe p99 against idle was a little lower with N client loops (16 CPUs: 1.04–1.09 against 1.06–1.19 with 15; 8 CPUs: 1.21–1.24 against 1.24–1.31 with 7; one round of each N reads 0.79 and 0.97, its idle p99 itself high), its absolute p99 within the same 100–126 µs; `check` and `race` alike (check 1.20–1.50 and 1.20–1.42, race 1.01–1.09 and 1.03–1.09 at 16 CPUs); at 8 CPUs seven loops did 2–4 % less of the storm's heavy work than eight, and home's longest storm turn was 1.26–1.80 ms with seven against 0.50–1.02 ms with eight. For N − 1: 16 loops beside home on 16 CPUs had several client loops in 2.9–6.4 ms turns at once in five of six storms (the three rounds, and three more of the storm alone at load average 1.1–1.4), home being busy there with some 18 000 accepts a second besides its jobs, where 15 had none such (0.57–0.79 ms, but 2.17 ms in the round at load average 19.5), and did as much heavy work or more (one storm of 16 lost a quarter of it); at 8 CPUs the longest turn of any loop was 0.70–1.98 ms with eight and 1.26–1.80 ms with seven, a wash. So N − 1 client loops run beside home, for the turn max that S5's gate judges: one CPU's worth is left to home and the threads that mostly sleep, at the cost above. (In `check` the longest turns, 11–13 ms, and 16.9 ms in the gate's rerun after the review, came from the walk of the arenas in a high-pressure relief, with 15 loops as with 16, whenever the kept memory, about 4 GB, passed the threshold, 4014 MiB here, during the load: §5.)

**Settings:** nice 0 (nice-19 SCHED_BATCH took 1.82 s for a 5 ms task under a hog [ws]); no pinning (pinned p99.9 0.38–1.7 ms [P]); timer slack 1 ns (overshoot 53 → 4 µs [P]); a blocker fills `CURLOPT_RESOLVE`, so libcurl spawns no resolver threads (*as built in S3*: one lookup per host at a time, its addresses serving new requests for 60 s, a failed lookup leaving the old ones; libcurl still looks up a proxy it takes from the environment).

**Rules:**
- **R1.** Every mutable object has one owner thread. Connections never migrate.
- **R2.** Per-loop objects cross threads only as a `struct handle`, which is dropped if its generation is stale. mcp2210 wrote to reused eventfds 1767 times in 0.37 s [M].
- **R3.** Posting transfers everything a message points to, including json-c trees, whose refcounts are non-atomic [T].
- **R4.** Besides single-writer gauges and metrics, SPSC log rings and the global body budget, `struct job` is the only shared mutable object: each field has one writer, with one atomic hand-off word per direction (`src/job.h` names each field's writer).
- **R5.** Immutable data (config, `SSL_CTX`, `mcp_static`) is published before start, or swapped by message and refcounted.
- **R6.** Every job ends in exactly one completion.
- **R7.** No lock is held across a syscall or O(n) work. The only lock is the blocker queue's.

```c
/** Cross-thread name of a per-loop object: never a pointer, never an fd. */
struct handle {
	uint64_t bits; /**< loop:8 | slot:24 | gen:32 */
};
```

**Turn.** Callbacks only flag and enqueue. Each turn: `epoll_pwait2` (≤ 128 events, zero timeout if work is pending); ≤ 256 inbox handlers (the rest wait on a local list); ≤ 64 timers; interactive ready-list steps round-robin until 500 µs; at least one bulk step, more until 1 ms; reap. A **step** is one recv/`SSL_read` (≤ 64 KiB) plus ≤ 8 cheap requests (or 100 µs), one TLS flight, one 16 KiB JSON parse slice, one 64 KiB result-escape slice (escaping costs 18 ms per 4 MiB [T]), one write, or one ≤ 250 µs task slice. Steps are timed per kind; one over 250 µs is an overrun (asserted in debug builds). A turn thus stays near 1 ms plus one overrun, under the 2 ms invariant.

*From S2b* (§8, §11.5) the bound is checked in units of work, not time, since a busy machine stretches any step: `loop.h` names them with their bounds per step (requests 8; bytes received 64 KiB, sent or queued by an application 256 KiB, of body taken in 64 KiB, of JSON parsed 16 KiB, escaped 64 KiB, copied whole 1 MiB; JSON values parsed or freed 256; accepts 32; from the review of S3, closes 32; from S3m, blocks or objects given back under memory pressure 256, one counting a unit per 128 KiB), steps count what they do and stop at the bound, and the statistics keep each unit's most in a step, with the most events (≤ 128), timers (≤ 64) and steps in a turn. The time budgets above still order the turn. Work that cannot be split counts in full where it happens, so the statistics can show a bound broken: a library's copy (json-c copies a string whole when it ends), an answer's text read whole, an application's `data()`. The review of S2b found the first version counted only work it had already capped, so no step could ever show over a bound.

## 2. Messaging

The only primitive: a lock-free intrusive inbox per loop plus one counter-mode eventfd. Producers push with a Treiber CAS; the consumer takes the whole list with one exchange, which rules out ABA [J2].

```c
struct msg {
	struct msg *next;
	void      (*fn) (struct loop *loop,
	                 struct msg  *msg);
};

static inline void
loop_post (struct loop *dst,
           struct msg  *msg)
{
	struct msg *head = atomic_load_explicit(&dst->inbox, memory_order_relaxed);
	do msg->next = head;
	while (!atomic_compare_exchange_weak(&dst->inbox, &head, msg));
	if (atomic_exchange(&dst->asleep, false))
		(void)eventfd_write(dst->wake_fd, 1);
}
```

**Sleeping.** Before blocking, the loop stores `asleep = true`, then loads `inbox`, and does not block if it is non-empty. All four accesses are seq_cst, so either the producer sees `asleep` or the loop sees the message. After waking it clears `asleep` and reads the eventfd only if epoll reported it [J1]. The taken list is reversed, keeping per-producer order. A gated push costs 96–115 ns against 460–486 ns with a write per push [P]; EFD_SEMAPHORE took 179 µs to drain 512 posts [M].

**Embedded messages.** A message continuing an exchange (progress, done, cancel) lives in its object beside a pending word. The poster does `fetch_or(bit)` and, only on 0 → non-zero, takes a reference and pushes. The handler unlinks the message, exchanges the word to 0, acts on the bits, and drops the reference. "Queued" and "what happened" are one atomic, so they cannot race; a burst is one message (srtview's poke storm [S]); posting cannot fail, so R6 holds under OOM [J2]. Messages that open an exchange (new connection, status query) are allocated; failure is a 503.

**Bounds and priority.** Inbox length is bounded by live objects, which admission bounds. Priority lives in turn order and the scheduler, so status, ping and cancel never wait behind the LLM. The blocker queue is `mtx_t` + `cnd_t` + a list capped at 256; full fails the request.

*As built in S3* (`loop.h`, `blocker.h`): the inbox as above, each message stamped at its post for the inbox delay metric, and the turn taking it after its events and before its timers. Its first users are blocker completions and the brainstem's orders: drain, statistics and the test stall, bits of one embedded message. The blocker queue takes POSIX's mutex and condition variable, which glibc's `mtx_t` and `cnd_t` wrap: ThreadSanitizer does not see the wrappers, and took the queue's own fields for races.

*As built in S4* (`loop.h`, `job.h`): the handles of R2. Each loop has a table of slots, each an object and a generation; `loop_handle()` names an object with a slot, the one freed last if any, the table doubling from 64 slots up to 2^24 and keeping what it grows to; `loop_lookup()` gives the object if the handle's loop number and generation match its slot's, else nothing; `loop_forget()` frees the slot and advances its generation, never to 0, so every copy of the handle goes stale. Each is O(1), and the table holds no more slots than objects named at once: the tool calls waiting for their jobs, one at most per connection. The handle's loop field is the loop's number, 0 for home and 1 for the client loop, which the brainstem sets before `loop_init()`. The tool call is the first user: an MCP request names itself to its job, and frees its slot as it cancels the job, so a completion that comes after finds nothing and is dropped. A job names its front's loop by pointer, as a blocker job does: that is the inbox it posts to, which outlives every job (§6). The job's two embedded messages are the second user of the pending-word scheme above, the brainstem's orders the first; the orders gained RELIEVE (S3m) and ALONE (S4).

*As built in S5*: the handle's loop field names client loops 1 to N, home being 0. New messages: the hand-over of a connection, home to a client loop, which the loop's handler only queues for a step to set up, and its give-back, which travel in the connection's own storage, so posting never fails (§3); a client loop's evictions, home to the loop, embedded in what they share, with a count as the pending word; the order OPEN, home's only; and a carrier job with WITHDRAW for a legacy cancellation (§4). The brainstem's loops live in storage it allocates, each laid with `loop_place()`, which initializes its atomic members once, at allocation, as `loop()` does for one declared (`hist.h`); every per-loop object holding atomics that askai allocates is initialized so too (stashes, MCP's counts, what home's door shares with the loops).

## 3. Network layer

**Accept.** Home accepts up to 32 connections per turn on one level-triggered listener and posts each to the lighter of two random loops among 1..N-1 (weight = connections + util‰/4, counted at assignment so bursts don't herd). EPOLLEXCLUSIVE sent 98.7 % of a trickle to loop 0 [J2]; SO_REUSEPORT never rebalances [P]. A spare fd absorbs EMFILE. Accept never pauses for idle clients (a client waited 62.7 s [T]).

*As built in S5* (`httpd.h`: home's door, `struct httpd_home`, and the client loops' servers, `struct httpd`; what they share, `struct httpd_hub`, is made before any loop starts and freed after every loop is finished):
- **Door.** Home binds the listener as it starts and adds it to its epoll for no events, so that a failure fails the start, as in S4, and listens, level-triggered, once the brainstem has every client loop running (the order OPEN); the endpoint's log line says so. An OPEN that comes with or after the order to drain leaves the door shut (review of S5: the first version added the listener at OPEN, so a failure there left askai running with no door, and an OPEN after the drain logged an error). An accept step takes at most 32 connections (`accepts`), fewer once 100 µs have passed, and only with the spare descriptor in hand: out of descriptors (EMFILE, ENFILE), home closes the spare, accepts in its place and makes room (below), and reopens the spare at once or, if no descriptor is free yet, as soon as a connection comes back or at the 5 s tick, listening paused meanwhile. Accept never pauses for idle clients.
- **Placement.** Home places each connection on the lighter of two client loops chosen at random (xorshift), or of two as light the one with fewer connections. A loop's weight is the connections home placed on it and has not had back, plus those it placed since it last sampled the loop's utilisation, plus a quarter of that utilisation in per mille. Home works the utilisation out from the time the loop's turns took, the sum of its turn histogram (single-writer, relaxed), over at least a second since the last look, as it compares the loop; so it needs no timer, and one request's millisecond is no load. A connection counts at assignment, and once more until the next look, whose utilisation then holds the work it brought: so a burst does not herd, and connections that come and go, churn, spread too, rather than go to the lightest loop until the next look (the first version, without that, placed 14.7 times as many on the lightest of 32 loops as on the heaviest in a storm; now 1.6 times, the heaviest being the one with the pipeline). With one client loop every connection goes to it.
- **Hand-over.** Home hands a connection over in storage of its own, a `struct conn` taken off its shelf of those given back (`shelf.h`) or allocated on a miss, with the descriptor, the client address's entry and whether it is on loopback, posted to the loop's inbox: posting never fails, and once warm nothing is allocated per connection, where S4's loop allocated and freed each, nor per client address, whose entries home keeps for reuse likewise. From the moment the loop takes it, the connection is the loop's for life (R1). The loop's handler only queues it; an interactive step sets up at most 32 a step (`accepts`, as S4's accept step did): `TCP_NODELAY`, its timer, its epoll entry (review of S5: the first version set each up, or closed it, in the handler, up to 256 a turn and counted in no unit). Once it has closed and its events are dispatched (`loop_release()`), the loop posts the same storage back to home, which counts the connection no more and keeps the storage for the next, until memory pressure frees it (§5). So home counts each loop's connections and each address's exactly, from placement to give-back, those on their way included. A loop that drains closes a connection home still places in that step, and gives it back, as it does those queued as its server stops; one handed to a loop that has stopped waits in its inbox until `loop_fini()` closes it and frees its storage, as home's loop is finished by then. None is lost or left open: `tests/askai.py` holds every loop's drain open with a head part way while clients come in as it begins, and each must be closed or answered while askai still runs.

**Process-wide limits** (S5). Each lives where it is decided without a lock, an O(n) walk on the hot path, or a message round trip before a client is served (R7):

| Limit | Where | Why |
|---|---|---|
| connections per client address (IPv4, or IPv6 /64; 256) | home's table of addresses, which counts at placement and give-back | exact, those on their way included; checked as home accepts |
| descriptor budget (connections + jobs in flight: all but 64 of RLIMIT_NOFILE and the two each client loop holds, its epoll and its inbox's eventfd, or half of fewer) | home: its count of connections and its jobs in flight | both are home's; a new client or an admitted job over budget makes room (review of S5: the first version left 64 alone, which 27 loops' own descriptors use up, so with 31 loops tool calls failed for want of a descriptor rather than evict idle clients) |
| LRU eviction under descriptor pressure | the loop whose least recently active idle connection is the least recently active of all closes it, as home asks (an embedded message with a count, the pending-word scheme); each loop publishes how many idle and since when the least recently active has (single-writer, relaxed) | home looks at every loop only under descriptor pressure; in a burst it treats a loop asked to close some as standing for when its next idle one began to, were their beginnings spread evenly, so the burst spreads over the loops and no loop is asked for more than it has idle |
| global body budget (256 MiB) | one atomic count in the hub, which each client loop takes from by compare-and-swap and gives back to | already shared in R4 |
| per-address body budget (a quarter of it) | an atomic count in home's entry for the address, which the client loops take from and give back to likewise; home makes the entry, and keeps it for reuse only once the address's last connection has come back, when no loop refers to it | the loops decide as bodies arrive; the entry outlives every use |

With several loops, LRU eviction is as near least recently used as the loops can tell home, with one exact: with 4, a burst of 60 tool calls under 128 descriptors for clients and jobs closed exactly the 60 least recently active of 68 idle connections, in 3 runs of 3. With 32 loops of two to four idle connections each it is coarser: a loop asked for more than it still has idle, some having turned busy, closes those it has, and of 21 runs of the same burst with 32 loops, 2 closed 59 rather than 60 and 1 closed a connection whose call was on its way; 10 calls on 115 idle connections under 96 closed 29 in 10 runs of 10, the 29 oldest in 6 and all but one or two of them in the others. The R4 exceptions this adds: the body budgets above (per address, as well as global); each client loop's published idle count and time and its eviction count (home adds, the loop takes); and a connection's storage, which moves between home and the loop that serves it by posting (R3), one owner at a time.

**Events: level-triggered**, with loop.c's MOD elision. LT costs 2.07 syscalls per request, ET 3.03 [P]. While a job runs or output is above high water, a connection watches only EPOLLRDHUP (`conn_rearm`, httpd.c:436-445), so it cannot spin [J1].

**TLS: OpenSSL 3.6**: ECDSA handshakes ~200 µs (RSA ~700), 14× on 16 threads, 21.6 KB idle with `RELEASE_BUFFERS`; GnuTLS lacks ML-KEM, mbedTLS is ~5× slower [P].
- TLS 1.3, ECDSA or Ed25519 cert; `RELEASE_BUFFERS | NO_AUTO_CHAIN | ENABLE_PARTIAL_WRITE | ACCEPT_MOVING_WRITE_BUFFER`; one ticket, no session cache; X25519MLKEM768; ALPN `http/1.1`.
- fd BIO with `read_ahead=1` (without it, two reads per record [P]); `SSL_has_pending` feeds the ready list.
- Handshakes are bulk steps on the owning loop (first flight 165–219 µs, second 35 µs [P]); placement spreads storms, ~0.65 ms per loop for 100 clients. RSA (659 µs first flight) needs `tls.allow_rsa`.

**HTTP/1.1.** Kept from httpd.c: resumable `head_length`, `parse_head`, `tchar`/`has_token`, constant-time auth, Origin defence, 100-continue, CORS/PNA [T]. New:
- parsing in place in `struct buf`, consumed by offset (a 1.12 s pipelining stall fell to 97 ms [T]);
- [M]'s parser contract: 0, ENODATA plus an offset, or an error that closes only that connection;
- chunked request bodies, which RFC 9112 requires [P];
- optimistic writes, arming EPOLLOUT only on EAGAIN; headers from fragments (printf cost 3–5 % [T]);
- `MSG_NOSIGNAL`, with SIGPIPE ignored [M].

**Stream interface** (S2): MCP sees only this, so h2 via nghttp2 inherits no HTTP/1.1 assumptions.

```c
struct stream_ops {
	int         (*head)    (struct stream *s,
	                        uint16_t       status,
	                        struct span    fields,
	                        size_t         length); /**< or STREAM_OPEN */
	int         (*data)    (struct stream *s,
	                        struct span    bytes);  /**< EAGAIN above high water */
	void        (*end)     (struct stream *s,
	                        int            error);
	void        (*waiting) (struct stream *s);      /**< a FIN now cancels */
	struct span (*field)   (struct stream const *s,
	                        size_t               i);
};
```

Upward: `on_head` (method, body length or `STREAM_OPEN`), `on_body` (decoded bytes, the last piece marked), `on_writable`, `on_cancel` (close, RDHUP, RST_STREAM). No upcall comes from within a downcall, so the application answers from any upcall or from its own steps; `on_cancel` never follows `end`. **SSE** is chunked `text/event-stream` with `X-Accel-Buffering: no`, id-less `data:` frames, and a `:` keep-alive every 15 s, under the 60 s SDK and nginx timeouts [P].

*As built in S2b* (`src/stream.h`), three things differ from the first sketch, each because HTTP/1.1 needs it and h2 does not mind:
- `head` takes the body's length: h1 frames a known length with Content-Length and an open one (`STREAM_OPEN`) in chunks, or for an HTTP/1.0 client until the close.
- The application names the request fields it reads, and `field` returns them, so the transport keeps their offsets and MCP parses no header.
- `waiting` marks a response that waits outside the loop, such as an upstream call. Only from then on does h1 take a half-close (RDHUP) as cancellation. Otherwise the step budget could make cancellation depend on timing: a cheap request deferred to a bulk step would be dropped for a client that pipelined and half-closed, where S2a answered it. In h2 a half-close ends every request, and only RST_STREAM cancels.

Settled in the review of S2b:
- **Output limit.** `data` may take the pending output past `out_max` only while the response is all of it and has not been told to wait (EAGAIN); otherwise such a write ends the stream and closes the connection. A response therefore goes out in pieces of any total size as the client reads, and a client that leaves pipelined responses unread is still cut off. The first version applied the limit to a response's own head and chunk terminator, which were separate writes, so it dropped every tool answer over 1 MiB.
- **Pieces.** MCP sends a reply a piece a step, each at most the step's share of sending (256 KiB), and after EAGAIN waits for `on_writable`. HTTP/1.1 counts the bytes an application queues as sent work.
- **Lists.** An application marks the fields that are lists (RFC 9110 5.3), such as Accept: they may come in several lines, and `field` gives the first. Every other field may come only once (400). A split Accept was refused before.
- **`on_writable`.** A response that ends there gets the next step, which takes up the connection's next request. Before, a connection whose response ended there with no output pending was left without events, step or deadline.

The application copies a body as it arrives, one memcpy per byte, so the transport can cut it out of its input and keep only the head; chunks are decoded in place, with CRLF-only framing and validated trailer fields. SSE answers `tools/call` when the client accepts `text/event-stream` and its era has Streamable HTTP: all but 2024-11-05, a legacy request without `MCP-Protocol-Version` counting as 2025-03-26, as the 2025-06-18 revision prescribes. The stream opens when the call starts.

**Limits.** Deadlines live on the heap and are never refreshed by single bytes.

| Limit | Default | Breach |
|---|---|---|
| head | 16 KiB, 64 fields, 10 s | 431 |
| body (per tool) | tunable, default 1 MiB; ≥ 4 KiB/s after 5 s | 413 |
| JSON (per tool) | depth 32, ≤ 1024 values, ≤ 1024 members per object (S2b), numbers ≤ 1 KiB (S2b review) | 400 |
| bodies in flight | 256 MiB global | 503 |
| idle keep-alive | 30 s, LRU eviction under fd pressure | close |
| per principal | 256 connections | refuse |
| pending output | pause at 256 KiB, close at 1 MiB unless one response is all of it | close |
| write stall | 30 s | close |

Connections are capped only by RLIMIT_NOFILE. These limits end three [T] problems: the slow-loris lockout, 830 MB of idle retention, and 585 MB from one body.

**WebSockets: no.** Streamable HTTP is the MCP standard every target client speaks, and in 2026-07-28 closing a request's stream *is* cancellation [P]. WebSockets would add a second framing, cancel model and auth path (browsers cannot set Authorization on them). Their one real gain, more than 6 streams per origin, comes from h2.

## 4. Jobs

```c
/** LLM call shared by its origin loop (front) and home (back): R4. */
struct job {
	struct msg       to_home;     /**< bits: SUBMIT, CANCEL */
	struct msg       to_front;    /**< bits: PROGRESS, DONE */
	struct list      hook;        /**< home only: principal FIFO */
	struct buf       request;     /**< front writes before SUBMIT */
	struct buf       result;      /**< home writes before DONE */
	struct handle    call;        /**< origin call slot; stale -> drop */
	uint64_t         principal;
	uint64_t         deadline_ns;
	_Atomic uint64_t progress;    /**< tokens:32 | queue position:32 */
	_Atomic uint32_t home_bits;
	_Atomic uint32_t front_bits;
	_Atomic uint32_t refs;        /**< front + home + each queued message */
	int16_t          status;      /**< home writes before DONE */
	uint8_t          class;       /**< interactive, background */
	bool             preempted;   /**< home only */
};
```

**`tools/call`:**
1. **Submit.** The origin loop validates (incl. base64 `Mcp-Name` [P]), builds the upstream body, allocates the job (refs = 2) and a call slot, posts SUBMIT, opens SSE.
2. **Admit.** Home takes ≤ 8 queued jobs per principal, ≤ 256 in total, only while the breaker is closed; otherwise DONE(busy) at once.
3. **Schedule.** Per-principal FIFOs with deficit round-robin (an [M] flooder pushed others from 1.2 ms to 10.7–40 ms); interactive first; S slots = `-np`. With S ≥ 2 one slot is reserved for interactive work; with S = 1 interactive preempts background, requeued at most once.
4. **Upstream.** Home runs it over http.c's curl bridge [T]:
   - `stream:true`, parsed by sse.c; empty proxy and `Expect:` [S];
   - `MAX_HOST_CONNECTIONS = S`, `MAXCONNECTS = S + 1` (askai kept 3000 idle sockets [T]);
   - deadline from dispatch plus a 60 s per-chunk idle limit (today's timeout counts queue time [T]; srtview's 3600 s held its lane [S]);
   - a 1 MiB answer cap, consumed ≤ 64 KiB per turn via `CURL_WRITEFUNC_PAUSE` (an 8 MB answer stalled the loop 29 ms [T]);
   - errors fail only their transfer (http.c:86 [T]); a breaker on refusals, timeouts, 5xx and stalls, half-open probing [S].
5. **Progress and done.** Home updates `progress` and sets PROGRESS; the front emits at most one `notifications/progress` per 100 ms. On DONE, the front looks up `call` and replies, or drops the result if the call is stale.

**Cancellation.** Close, RDHUP, a write error or the output cap frees the call slot (gen++) and sets CANCEL; home dequeues the job or removes its curl handle (5/5 cancelled today [T]) and sends DONE(cancelled). Legacy `notifications/cancelled` goes through home's (session, requestId) registry. RDHUP cancels in every era: without resumption a legacy result is lost anyway [P]. Status and `tasks/get` are one ~5 µs round trip to home [P].

*As built in S4* (`job.h`, `home.c`, `mcp.c`), a job has the fields above but `principal`, `progress`, `class` and `preempted` (S6). It adds the front's loop, set as the job is made; home's own curl transfer, admission time and hook among the answers held back (step 3); and the answer's HTTP status, which home writes before DONE. The steps:
1. **Submit.** The front validates, opens the event stream and builds the upstream body a slice a step, as in S2b; then it takes a job (the one let go of last, else a new one) and a call slot, moves the body into the job's request, sets the deadline from `--timeout`, sets `refs` to 2 and posts SUBMIT. Out of memory for either, the call ends at once with a JSON-RPC error.
2. **Admit.** Home counts the job, and ends it at once while it drains, or as busy with `--max-calls` jobs (256) in flight; else the job joins the registry of jobs in flight, admitted. A bulk step hands the admitted jobs' requests to the curl bridge, first in first out, eight a step (`reqs`); the bridge starts two a step. Home ends a running job at its deadline itself, as timed out, by a timer for the oldest: the running jobs are in the order of their deadlines (with several fronts, nearly so). libcurl gets no timeout of its own, as one short of memory lost a transfer's (review of S4: a job 17 s past its deadline kept its place among the `--max-calls` until shutdown). Home's messages only admit, refuse or move jobs, in O(1): a call into libcurl costs some tens of µs, and the race profile's bursts of submits and cancels made home turns of up to 4.6 ms while the messages made them.
3. **Done.** Home takes the answer into the result, up to 16 MiB, as much a step as its share of receiving (64 KiB) allows: libcurl holds the rest back until a later step lets it on (`CURL_WRITEFUNC_PAUSE`, which §4 planned for S6; the review of S4 found home's gathering uncounted, and a step that took in 352 KiB). Home then writes the status into the job, or else the reason in the result's place, as the front wrote it before (too large, timed out, the transfer's error), and posts DONE, keeping its reference. A job that ends cancelled ends with its result empty, as the front reads none (review of S4: a drain had the front copy a partial answer of up to 16 MiB in its handler).
4. **Reply.** The front frees the request's storage and looks the call up. If it has gone the completion is dropped; else the call frees its slot and parses the answer a slice a step, or replies at once: a busy job is a tool error ("Too many tool calls are under way; try again in a few seconds."), a failed one carries its reason, and one a drain cancelled ends with the shutdown error.
5. **Let go.** The front posts CANCEL once a job: before DONE to cancel it, freeing the call slot and keeping its reference for the completion; after DONE once it has read the result, dropping its reference. Home, on CANCEL, ends a job not yet started at once and has a bulk step cancel a running one, eight a step (DONE(cancelled)); once the job has ended it gives the result's storage back to its own stash and drops its reference. So each buffer's storage is taken and given back by one thread: the request's by the front, the result's by home, and no storage moves between stashes (§5).
6. **References.** Whoever drops the last returns the job to its front's spare list: home, which usually does, through the front's inbox with a RETURN bit and no reference. A spare job holds no storage, and goes back to the allocator only in a relief, as finished requests do.

The cancellations of S3 (close, RDHUP, write error, output cap, drain, legacy `notifications/cancelled`) all reach the one place that lets a request go. With one client loop the (session, requestId) lookup stayed on it, as an O(n) walk of its calls; S5 moved it to home's registry (below). Home counts its jobs, submitted = completed + cancelled + rejected + in flight, and logs the counts as it stops; the front counts the calls it cancelled while they waited and the completions it dropped, which agree once the jobs have ended. Deviations, each for the reason given: CANCEL also lets go, and RETURN exists, so that the result's storage goes back to the thread it came from (a job is four messages, two each way, where the design has two); the scheduler is admission and FIFO only, with no principals, classes, preemption or breaker, and the upstream is not streamed (S6).

*As built in S5* (`job.h`, `home.c`, `mcp.c`), legacy `notifications/cancelled` goes through home's registry, whatever loop it comes to:
- **Key.** A job carries its call's key, which the front writes before SUBMIT: the call's `Mcp-Session-Id` field, if present, and a line break, which no field holds, then its request id's JSON. Session and id must both match, as before, so one client cannot cancel another session's call; a field absent and one empty differ, as before. With the key the front writes its hash, seeded at random before any loop starts (`mcp_static`) so that no client can pick keys that crowd a bucket: home's handling of a message then costs the same whatever a key's length, a head's worth at most (review of S5: home hashed the keys itself, and a notification's `requestId`, which nothing checked, could be as long as a body; 320 ids of 1 MB made home turns of up to 233 ms, where it now takes 62 µs).
- **Registry.** Home chains the jobs in flight, from admission to their end, in buckets by their keys' hashes: `--max-calls` buckets, rounded up to a power of two, at most 65 536. A lookup is O(1), and bounded by the jobs in flight at worst.
- **Withdrawal.** A `requestId` that no request may have, neither a number nor a string of at most 1 KiB, names no call: the loop answers 202 and posts nothing. Otherwise the loop a notification comes to takes a spare job as a carrier, writes the notification's key into it and posts it to home with WITHDRAW, then answers 202 at once. Home ends each job in flight that the key names as WITHDRAWN, at once if it has not started, else by the bulk step that cancels the jobs dropped (its upstream transfer cancelled), and returns the carrier to its front (RETURN). The call's front, on DONE(WITHDRAWN), ends the stream quietly, as the walk did: 202 for a JSON POST, an event stream that ends without an event. A job its front let go of already is left to that cancellation; a key that names no job, as its call has ended or has yet to reach home, does nothing, as before. Home counts a withdrawn job as cancelled; the front, which cancelled nothing, counts neither a cancellation nor a dropped completion.
- The client loop's O(n) walk is gone; its list of calls under way stays for the drain, which ends them a share a step.

*As built in S6* (`home.c`, `job.h`, `ai.c`, `mcp.c`, `http.c`): the scheduler, streamed answers, the breaker and progress. Classes, the slot reserved for interactive work and preemption wait for S8's tasks: until tasks exist every tool call is interactive, and they would have nothing to act on (§11.1).
- **Principal.** A job's principal is its call's MCP session, the `Mcp-Session-Id` field, when it has one, else its client's address as the limits per address key it (IPv4, or IPv6 /64), which the transport gives the stream (`stream.h`). The front writes it into the job before SUBMIT with the key: the session's length, as the session begins the key, or the address, and a hash, seeded as the key's. Home finds the principal's entry by the hash, in as many buckets as the registry has, and compares the session's bytes or the address exactly, a head's worth at most, as it does a key. An entry exists while its principal has jobs queued, the first of which tells who it is, and goes on home's shelf for reuse after (§5). One client may open many sessions for many shares (§10, risk 9).
- **Admission.** Home ends a job at once while it drains (cancelled); with the breaker open (below); with `--max-calls` jobs in flight, or with eight queued for its principal, as busy, the busy tool error with its retry hint (§10). A job that a free slot takes at once, the breaker closed and no principal waiting, is ready: it queues for none, and starts before the ring's, so that a burst of calls that free slots take at once is not refused, while no queue holds more than eight. Else the job joins its principal's queue at the back, and its place there is its progress; a principal new to the ring joins it at the back. (Review of S6: the cap first counted only the jobs beyond the slots free, which let a principal queue 8 + S − 1, and every principal so while a probe ran, the slots then free but idle; a job's removal from its queue moved up to S + 6 a place, where seven at most was claimed, and S may be 65 535.)
- **Slots and starts.** S is the number of upstream calls home makes at once. `--slots N` sets it; else home asks once as it starts, through the curl bridge, for llama-server's `GET <scheme://host:port>/props`, its `total_slots`, but only for the protocols llama-server speaks, all but `gemini` (a real llama-server answers `/v1/responses` and `/v1/messages` too), and an endpoint not on a well-known cloud API's host (OpenAI, Anthropic, Azure OpenAI, OpenRouter, Groq, Mistral, Together, DeepSeek, xAI, Fireworks), and parses the answer (1 MiB at most) a slice a step; failing that, or before the answer, S is 4. The answer may take the calls' timeout, and 10 s, at most (review of S6: a `/props` that never answered left the S in use unlogged, and libcurl's cache unbounded, for good). The log says the S in use and why, once it is known. libcurl's cache follows S from the start: `MAX_HOST_CONNECTIONS` = S and `MAXCONNECTS` = S + 1, which bounds the idle upstream sockets that failed TSan's `answers` descriptor check in S5. Whenever a slot frees, a bulk step (eight a step, `reqs`) starts the jobs ready, then takes the ring's first principal, starts its oldest job and moves it to the back, and none while home drains (review of S6: the drain's cancellations freed slots, which started queued jobs upstream only to cancel them): deficit round-robin with a quantum and a cost of one job. The cost is the job rather than its slot time: the slot time is known only as the job ends, and charged then it would leave deficits negative over many rounds, so that finding a principal that may start one would no longer be O(1), or a slot would idle while jobs wait. A job's slot time is bounded by `--max-tokens` and its deadline, and a call is a client's unit of interaction: a principal with one call at a time waits one round of the principals queued at most. The price is that a principal whose calls generate longer answers takes more slot time a round (§10, risk 10). Every message handler stays O(1): admission's lookup, and a job's removal from its queue (cancellation, withdrawal, deadline), which moves the seven at most behind it a place nearer. The test aid `--test-fifo` puts every job in one principal's queue, with no cap but `--max-calls`: S4's first in first out, the flood profile's contrast (§8); its jobs keep the places they were queued at, as moving them all up would cost O(queue) a dispatch.
- **Deadline.** `--timeout` bounds two waits: a job's in its queue, from its submission, as the front sets it (S4), after which it ends as timed out waiting for a slot; and its upstream call, from its start, after which home ends it as timed out, cutting its transfer. Once an answer has begun, a pause of `--chunk-timeout` (60 s) between its bytes ends it as stalled, so a silent upstream holds a slot that long at most; before the first byte only the deadline bounds it, as llama-server sends nothing while it processes a long prompt, which on modest hardware takes minutes. A call so waits twice the timeout at most. The jobs in flight are on one timeline in the order of their deadlines, a job moving to its end as it starts (with several fronts, nearly so), and one timer serves its first; the answers under way are on a list in the order of their last bytes, and one timer serves the quietest.
- **Streaming.** Every protocol asks for a streamed answer: `stream: true` in the body, set after `--extra` is merged, so that `-x` cannot turn it off; Gemini by its URL, `:streamGenerateContent?alt=sse`, which a `-u` URL ending in `:generateContent` becomes, its `alt` whatever it was (review of S6: an `alt=json` stayed, and Gemini's JSON array of chunks then read as no answer). An answer of status 2xx and `Content-Type: text/event-stream` is read as events; any other, from a server that ignores `stream: true` or an error's JSON body, is gathered whole and parsed by the front as before. Home takes a stream in as before, a step's share of receiving and `CURL_WRITEFUNC_PAUSE`, into the job's wire, and holds it back too while a share of it (64 KiB) waits to be read. A bulk step reads the streams in turn, each as far as the step's shares of parsing (16 KiB, the lines' framing included) and of values allow: lines; a data line's data joined to its event's in place, moved down over the line breaks and field names; and at a blank line, or the stream's end, the event's JSON, parsed a slice a step with home's own tokeners (`jb_parse_some()`) and freed likewise. `sse.c`, which twinception keeps, is not reused: it copies what it is fed into a dstr, and hands on every event of it in one call, however many. `ai_event()` hands the event's text to the job's result, checked to be UTF-8 (json-c lets overlong forms through) and copied (`copy`), up to the 16 MiB cap, which now holds the text; and says what else it says: its stop reason, the end, or an error. An error event ends the job with its message, "Upstream error (HTTP 200): …", as a whole answer's error does, and cuts the transfer, which the upstream sees as a hang-up; so does text that is not UTF-8, and an event that is not JSON text, whose text json-c finds no UTF-8 or cut short, as a whole answer's would; and home short of memory for an event ends the job so (review of S6: such an event was skipped, and the call answered with text missing). A stream that ends, its transfer whole, before an event says the answer has ended (chat completions' `finish_reason` or `[DONE]`, Responses' `response.completed` or `response.incomplete`, Anthropic's `stop_reason` or `message_stop`, Gemini's `finishReason` or `blockReason`) is cut off, as a transfer cut short is: "Upstream request failed: Transferred a partial file: the stream ended before the answer did", a failure to the breaker (review of S6: it passed as the whole answer). Each event of JSON is a chunk (`askai_upstream_chunks_total`), and each that adds text a token, which the progress counts (review of S6: every event counted, Anthropic's six of an answer's frame among them). At the end home finishes the text as `ai_answer()` does a whole answer's: the note after one the output token limit cut short, or "The model returned no answer (stop reason: …)." for none; and completes the job as TEXT. The stop reason is kept up to 37 bytes, longer than any the providers name (review of S6: 21 bytes cut Anthropic's `model_context_window_exceeded`, so that the text differed from a plain answer's). Per protocol: chat completions' chunks, the first completion's choice (`index` 0, should `-x` ask for more with `n`; review of S6: `choices[0]` of each chunk interleaved them), its `delta.content` (or its text parts) and `refusal`, `finish_reason`, `[DONE]`; Responses' `response.output_text.delta` and `response.refusal.delta`, `response.completed` or `response.incomplete` with its `incomplete_details.reason`, `error` and `response.failed`; Anthropic's `content_block_delta` of `text_delta`, `message_delta`'s `stop_reason`, `message_stop` and `error`; Gemini's chunks, read as whole answers' `candidates[0]`, thoughts left out, `finishReason` or `promptFeedback.blockReason`, and `error`.
- **Where the answer is parsed.** A stream's on home: it reads the events there anyway, for the progress and the error events; the cap is then the text's, where the events' JSON is many times the text; and the front only escapes the text into the reply, a share a step, straight from the job's result, with no copy of its own (a plain answer's text it copies whole, `copy`), and lets go of the job once that is done. A plain answer is parsed on the front, as before.
- **Breaker.** One for the upstream, on home. A failure is a transfer's error (connection refused, reset or unreachable, a host that cannot be looked up, the server's close mid-answer), a timeout (the deadline, or the chunk timeout: a stall), or an answer's status 5xx or 429; an answer cut off at the cap, or home short of memory, is no failure, and an error event is the upstream's answer, a success. After five failures in a row, or one whose answer had `Retry-After` (libcurl's `CURLINFO_RETRY_AFTER`), it opens, for what `Retry-After` asked, or else for the backoff, a second at first and doubling to a minute. While it is open, admission ends a job at once with a tool error, "The upstream is unavailable; try again in N s.", counted as rejected, and the jobs queued as it opened end so too, a share a step, rather than wait out a spell whose end promises nothing; the jobs running finish, their outcomes no longer counting. Then it is half-open: jobs are admitted and queue, and the first to start is the probe, alone until its answer begins: a status other than 5xx or 429 is its success, which closes the breaker, resets the backoff and starts the jobs queued, however long the probe's answer then streams (review of S6: judged at its end, a streamed probe held the other slots idle for its whole generation); its failure, at its end, opens it again for the doubled backoff. A job cancelled counts neither way; a probe cancelled lets the next job probe. Its state, opens and probes are in `/metrics`, and its transitions in the log, which limits each call site's lines (§6).
- **Progress.** Home publishes a job's progress in its atomic word, as §4's sketch has it: its place in its principal's queue, from 1, while it waits, and its answer's tokens, shifted 32, as it runs, an event with text or with the model's thinking being a token (`reasoning_content` or `reasoning` in chat completions, `response.reasoning_text.delta` or its summary's in Responses, `thinking_delta` in Anthropic's, a part marked `thought` in Gemini's), with JOB_THINKING, bit 31, set while the latest was thinking (from the first real run: a reasoning model's thinking left its progress at 0 for as long as it thought); and for a front that asked, as the front marks the job of a call that has a `progressToken` and an event stream, it sets PROGRESS on the pending word of the job's message to the front, one message a burst, as DONE (§2). The front then notes it, and writes `notifications/progress` on the call's event stream at most once every 100 ms a call, by the timer that serves the keep-alives: its `progressToken`, as the request gave it (a string of 1 KiB at most, or a number, as an id), a `progress` that grows with each notification (the places the call has moved up since the first it gave, then that and the tokens), and a message, "queued, position k", "thinking, n tokens" or "generating, n tokens", llama-server sending a token a chunk. A job ready posts none until it starts. Only while the call waits for its job: none after its result, none once it is cancelled, as a job whose call has gone finds no handle and home posts none for a job dropped or withdrawn, and none in a JSON reply. Output the client has yet to read holds a notification back until it drains. The event stream opens for a tool call as before, so a call without a token gets what it got.
- **Cancellation.** A job cancelled or withdrawn while queued leaves its queue at once, in O(1), and never reaches the upstream; one running is cancelled by a bulk step as before, its transfer cut, which the upstream sees as a hang-up mid-stream. Home counts those whose request had gone upstream (`askai_upstream_cancels_total` and the jobs' log line as it stops), which the harness's `jobs` clause holds against the upstream's own count (§8).

Deviations, each for the reason given: no classes, reserved slot or preemption (S8); the cost unit is a job; `--timeout` bounds the queue and the upstream call apart, and the chunk timeout starts with the answer; the answer cap stays 16 MiB, now of the text (an open decision, measurements); the place a notification gives is the call's in its principal's queue, which home can keep in O(1), not in the dispatch order across principals, which it cannot; a job is still four messages, PROGRESS sharing DONE's.

**Tasks** (the engine's interface) are ≤ 250 µs steps on the bulk list, placed by power of two choices at submit and re-placed at a slice boundary when the local backlog exceeds 2 ms (local-only placement diverges past one core of demand [ws]). Unsliceable calls go to the blocker.

**Children** (S6m, for the man tool; `child.h`): `pidfd_spawnp` into a session of its own, with an empty signal mask and every action the default (askai blocks every signal but the faults' and ignores SIGPIPE, which a child would inherit), stdin and stderr `/dev/null` and no other descriptor (`addclosefrom_np`); the pidfd and the output pipe's read end on the loop of the call that spawned it, the output read a step's share of `recv` (64 KiB) a bulk step into a capped buf; reaped by `waitid(P_PIDFD)`, no SIGCHLD; its process group killed with SIGKILL past the cap, at the deadline, or as its owner lets go of it, and only before it is reaped, after which its id may name another group: man's pipeline (`groff`, `troff`, `grotty`) are its children, which `pidfd_send_signal` would leave running. A global cap of 16 alive, an atomic, past which a man call is answered as busy. A spawn blocks its loop until the child has executed (`CLONE_VFORK`): 96 µs on average and 117 µs at worst over 30 spawns of man, within a step's share, so it runs in the step rather than on a blocker. A child let go of is freed once reaped; one alive as its loop stops is killed and left to the process's exit. **git** (S8): the same, with SIGTERM before SIGKILL at the deadline.

**Manual** (S6m, with the user, after the first cut: `manual.h`): the man tool's pages, each rendered once and kept, in one table the client loops share under a mutex, held for a hash lookup or insert and never across a syscall. A call's name and section are an alias; man finds its file (`man -w`, which follows `.so` stubs and symlinks), and the file keeps the page (`man -l -- FILE`), so every name a file is found by shares one rendering. A file keeps eight names at most; a name past those is found anew each time it is asked for, its page still the kept one, so that case variants (man matches names and sections without regard to case) cannot grow the table without bound. A page is immutable and counted: the table holds a reference, and so does each call that replies with it, so that a page replaced meanwhile lasts until the reply is out. A kept page is given as long as `stat()` finds its file's device, inode, size and ctime as they were when man began to render it: 0.3 ms for `pthread_create(3)`, 2.3 ms for `bash(1)` and 5.5 ms for `gcc(1)`'s 1.48 MB, the escaping and sending in steps as for any answer. Else the call waits for a fetch, as it does for a new alias: on the loop of the call that began it, the find, then the render unless the table has the file's page as the file is, then the output copied into a page of its exact size and made UTF-8 text, a step's shares of `copy` and `escape` at a time. Calls for the alias meanwhile wait for that one fetch (eight at once for a cold `epoll_ctl(2)`: 34 ms each, and one render), each posted its outcome, the page or why there is none, to its own loop, which looks the call up by a handle, as a job's completion does. A fetch goes on when its calls go, and its page is kept; failures are not kept. Once an alias's finding is older than the recheck (600 s; `--test-man-recheck` as a test aid), the next call gets the kept page and starts a fetch in the background, so that a page installed since, in a directory man searches first, takes over. A cold page costs a find of about 17 ms before its render (30 to 40 ms for section 3, 0.2 s for `bash(1)`, 0.7 s for `gcc(1)`), and a new name for a kept file the find alone. Pages render as UTF-8 (`LC_ALL=C.UTF-8`), its box drawing and typographic characters adding 0 to 4 % to a page, and are cut at 2 MiB, so that `gcc(1)` comes through whole. The manual releases nothing, under memory pressure either: the system's pages bound it (all of the user's English ones render to 136 MiB).

**Timers:** a 4-ary heap per loop, one entry per object, drives `epoll_pwait2`. Activity only stamps `last_active` (coarse clock, 4 ns [P]); an early-firing entry re-inserts itself. curl uses home's heap. This replaces httpd's O(n) tick and timerfds (3.6 µs each [P]).

/** Binary byte buffer for sockets, TLS and pipes; [head, tail) is readable. */
struct buf {

struct span {

/** At least @p min free bytes at the tail, doubling up to @p max; empty on ENOBUFS. */

buf_reserve (struct buf *buf,

Also `buf_commit`, `buf_peek`, `buf_consume` (resets when empty), `buf_trim` (shrinks to what the readable bytes need, gives the storage up when empty) and `buf_wipe` (secrets only; nothing else zeroes). Compaction happens only when a reserve fails and `head ≥ cap/2`: amortized O(1). `max` is the backpressure signal. recv and `SSL_read` fill the reserved span directly [T]. This replaces mcp2210's buf (linear growth, zeroing, memmove per consume [M]) and dstr on the I/O path (UTF-8-only, 255 reallocs to reach 4 MiB [T]); dstr keeps text.

**Memory retention** (the user's directive at S3m, §11.6; it replaced "no pool at first", whose buffers were trimmed when idle and after any request over 64 KiB, with `mallopt(M_MMAP_THRESHOLD, 128 KiB)`). Freeing and allocating every turn, or a little less often, is not wanted: threads hold on to their working space, and give back some of what they accumulate only when a memory pressure mechanism finds it time for preventative action. An idle connection costs ~300 B, ~22 KB with TLS [T][P], and holds no buffer.
- **Stash.** Buffer storage comes in power-of-two classes from 4 KiB to 32 MiB; larger storage is allocated and freed as it is. Each loop thread has a stash (`struct buf_stash`, `buf.h`): per class a LIFO list threaded through its blocks. Storage a buffer gives up goes to its thread's stash, and storage it needs comes from there first: `buf_reserve` grows into a class's block, copying only the readable bytes, and `buf_free` gives the block back. A connection gives its output's storage back once sent and its input's once idle, so 10 000 idle connections hold no buffers. A finished request gives back its body, upload, response and reply, and is itself kept for reuse with its answer's dstr, cleared rather than freed, and its pre-scan's and reaper's arrays; the request that ended last is reused first, so steady requests reuse the same few and only those keep a large answer's text. Every tokener goes back to its pool (§5 JSON), its string buffer kept. The timer heap keeps its slots. So once warm, a steady load makes no allocator call for buffers (S3m: none of askai's own per cheap request, from 10 allocations and 6 frees; json-c's own remain).
- **Bound.** What a stash keeps and its buffers hold stays within twice the most its buffers held at once: a miss that would pass that first gives back the stash's largest blocks. Each class would otherwise keep its own peak, and work that moves between classes would pile up a peak per class. Twice, so that the blocks a growing buffer leaves behind, and work alternating between two mixes of classes, cause no churn.
- **glibc** (`serve()`): `M_MMAP_THRESHOLD` 32 MiB, the most it takes; `M_TRIM_THRESHOLD` −1; `M_TOP_PAD` 64 MiB. glibc would otherwise map and unmap each block over 128 KiB on its own, give back a heap's top as frees reach it and a thread's heap once all of it is free (one `check` run in five lost 25 MB of its kept peak so), and grow a thread's heap a page and an `mprotect` at a time; it pads only a heap's creation, so no smaller pad does. What is freed stays for reuse, stashed or not, and resident memory plateaus at the working set's peak, the stash's share within the bound above. The pad makes every thread's heap writable whole, which counts against RLIMIT_DATA, RLIMIT_AS and a strict commit limit (`vm.overcommit_memory` 2), so under any of those it stays glibc's 128 KiB: the review of S3m found requests failing there that S3 served.
- **Pressure.** The brainstem works out a level once a second, none, high or critical (`enum buf_pressure`), from inputs that each move with hysteresis, and publishes the highest in an atomic, `buf_pressure`, which the loops read as they relieve it:

| Input | High from / below | Critical from / below |
|---|---|---|
| resident memory, of `--memory-high` | 100 % / 75 % | 200 % / 150 % |
| RAM in use: MemTotal less MemAvailable | 90 % / 85 % | 95 % / 90 % |
| cgroup v2: memory.current, less the inactive file cache (memory.stat) the kernel reclaims as it needs, of the lower of memory.high and memory.max, the fullest of the process's cgroup and its ancestors | 90 % / 85 % | 95 % / 90 % |
| memory PSI, some avg10 | 10 % / 5 % | 40 % / 20 % |

  `--memory-high` defaults to a sixteenth of the memory the process may use (the lowest limit of its cgroup and its ancestors, else RAM), at least 256 MiB, the default body budget, which bounds the working set the default limits allow. Where MemAvailable is missing (before Linux 3.14) the system's input stays at none. A service sharing a modest machine so keeps no more than a sixteenth of it in reserve while nothing else wants memory, and the system's and the cgroup's inputs act as soon as something does. The test aid `--test-pressure FILE` raises the level to the number the file holds.
- **Relief.** When the level rises, and every 10 s while it lasts, the brainstem orders the loop to relieve it, a bit of its order message; it frees nothing of the loop's and takes none of its locks. The loop's relief is bulk steps of at most 256 units of release work, the `release` unit, which counts a block or object given back as one unit per 128 KiB and at least one: unmapping a 32 MiB block, glibc's own mapping, takes 1.1–1.4 ms, so it takes a step alone (review of S3m: counted as one, sixteen took a 19 ms step). First the pooled tokeners whose string buffer outgrew a slice, one a step, then the requests kept for reuse, then the stash's blocks, the largest first, then the trim, a step of its own. At high pressure they give back what went unused for a window: the loop begins one every 10 s, and a class's or the requests' count kept unused is the fewest kept over the last window and this one so far, so even an episode's first relief gives back what sat unused (review of S3m: it gave back none, counting from the last relief); at critical pressure all of them, every tokener too. While pressure is critical, storage given up goes straight back to the allocator rather than to the stash, and a connection that waits trims its buffers to its bytes. The relief stops if the pressure clears, and without pressure no trim runs. `malloc_trim(0)` gives back the free pages in every arena and the top of the main one, but not the top of a thread's arena, which glibc trims only as a free of 64 KiB or more meets its threshold: so the trim lowers the threshold and the pad for one such free, then restores them.
- **Where the trim runs** (measured): on the loop, as a bulk step, 18–22 ms after the check profile's dense bodies, about 350 MB. On a blocker, the loop waited as long for its arena's lock, as each of its requests allocates (probe max 20.3–21.6 ms, against 18.0–21.2 ms on the loop), so it stays on the loop. The brainstem may not take a loop's lock, so it only orders; with N loops (S5) it should order one trim once every loop has released. (S5 walks on a blocker after all: with N arenas a loop waits only for its own; below.)
- **Across threads** (S4). A stash counts the storage its buffers hold (`held`) as they take and give it back. A block that one thread takes and another gives back stays counted by the first for good, while the second's count falls short, stopping at 0. Storage moving between home and the front would so leave home's count, and with it the bound, rising; and storage moving one way, home taking a result's and the front giving it back, would cost an allocator call a job on each side. So S4 moves none: a job's request is taken and given back by the front, its result by home, which the front tells when it has read it (§4). The count still stops at 0, as the thrift store below would want.
- **Trims take turns** (S4). Each loop's relief ends in its own trim, as only a free on a thread trims that thread's arena's top. The trim changes glibc's settings for the whole process, so two at once could have one restore them under the other: a loop that finds another trimming tries again a millisecond later, through an atomic flag that no thread waits on (R7 holds: nobody blocks on it). `malloc_trim()` walks every arena, so a loop whose release ended before another loop's walk began leaves the walk out, and trims only its own arena's top; an atomic count of the walks begun tells (review of S4: the second loop walked both arenas again). A walk still takes each arena's lock in turn, the other loop's too, which S5's one trim once every loop has released keeps to one walk an order.
- **One trim a relief** (S5), replacing the turns. The brainstem begins a relief only once the last has ended, and none while a loop starts: it sets a countdown to the loops it orders plus one, and orders RELIEVE to every loop, home included (review of S5: a loop that came to run between the count and the orders was ordered but not counted, and its extra count down wrapped the countdown, so that no relief began again). Each releases its own surplus in bounded steps as before, home its connections and client addresses' entries kept for reuse (§3) where a client loop has its requests and jobs, then leaves a 64 KiB block of its own arena on a lock-free list and counts down (`brainstem_relieved()`): it ends its share early if the pressure clears, but always counts down. The last to count down runs the one trim: a bulk step for each block on the list, which it frees into the arena it came from with the threshold and the pad lowered for that free alone, trimming that arena's top (only such a free does); then the walk of every arena with `malloc_trim(0)`, which needs no setting lowered, on a blocker, whose job lies in static storage rather than a loop's, as a blocker still busy at shutdown is left to the process's exit after the loops' storage has gone (review of S5); then, the blocker's job back, it logs what the relief gave back and lets the next relief begin (`brainstem_trimmed()`). With one loop a walk on a blocker held the loop as long as on it (S3m, above), as the loop waited for its own arena's lock; with N loops the walk takes each arena's lock in turn, so a loop that allocates waits only for its own arena's part. In `check` with 16 loops, each keeping a `dense` body's 300 MB (below), the walk took 200 ms: on the loop, as the first version ran it, that was a 178 ms turn and §8's `outliers` clause failed; on a blocker no loop's turn passed 12.4 ms (16.9 ms in a later round, 8 loops over 2 ms). Little was at the arenas' tops (each block's free took under 0.1 ms there): a thread arena of that size spans several heaps, of which only the last has a top. Should no blocker take the walk, the loop walks. So one thread alone changes glibc's settings, and only for one free at a time, nobody waits on another (a relief due meanwhile waits for the brainstem's next look, a second later), and a relief walks the arenas once however many loops there are. Freeing another arena's block takes that arena's lock for the free, as the walk does. The loop that trimmed counts the trim; each loop counts its relief.
- **What stays** (S5). Each thread's glibc tcache keeps up to seven small blocks of each size class, which no call gives back but the thread's exit: after a storm and a critical relief about 110 KiB a client loop of 32 stayed resident (tcache off, 1.8 MB stayed in all, against 5.4 MB with it), so the harness allows 256 KiB more per client loop (§8). Each thread keeps its working space in its own arena, so N loops keep up to N peaks: in `check`, whose `dense` bodies (with `--max-values` raised) take about 300 MB of json-c values each and come on new connections, which home spreads over the loops, the peak was 2.1–2.4 GB with 7–8 client loops and 3.7–4.2 GB with 15–16, against 0.37 GB with one; memory pressure, from a sixteenth of RAM by default, gives it back. With the default value limit a body holds at most 0.7 MB of values. Each client loop also costs about 0.55 MB resident from the start, mostly its histograms (the loop's metrics and statistics, and its requests' times by method): idle, askai held 11.8 MB with one client loop and 28.9 MB with 32. Under RLIMIT_DATA it costs about 2.3 MiB of the data segment, with its 1 MiB stack, its arena and its log ring, and `--loops` bounds that.
- **What home keeps** (S6): the principals' entries on a shelf, and its own tokeners for the streams' events; and each running stream's wire, whose storage, as the result's, comes from home's stash and goes back to it. A relief frees the entries and the tokeners (`home_relieve()`), as a client loop frees its requests and its tokeners.
- **Metrics** (§6): per loop the stash's retained bytes, hits and misses, the bytes it released, the requests kept for reuse and the bytes they and the pooled tokeners hold, and the reliefs and trims and their time; the level, each input's level, and the inputs. What glibc keeps free shows only in resident memory.

**JSON.** json-c and jb.c stay, with one reused tokener per loop (per-parse locale setup cost 2 % [T]).
- A streaming pre-scanner counts values and depth outside strings. 1024 values parse in ~95 µs and free in ~30 µs [J1]; cost tracks values, not bytes (4 MiB of strings: 5 ms; of small objects: 278 ms + 103 ms free [T]). Bodies over 16 KiB parse in slices.
- mcp.c splits into an immutable `mcp_static` (pre-serialized tools/list, discover, initialize, serverInfo `_meta` bytes) and per-loop state, removing the shared `json_object_get` sites at mcp.c:173, 368, 423, 488, 491 [T][J2].

*As built in S2b:*
- **Tokeners.** Each loop keeps a pool of up to four reused tokeners. Sequential parses use one, as designed. Two sliced parses cannot share one: a tokener holds its parse's state, and with one per loop every body would wait for another's whole parse. json-c keeps a tokener's buffer of the longest string it has seen, so until S3m's review a tokener went back to the pool only after a parse of one slice, and a larger parse freed it: a tool call with a 300 KB prompt and a large answer then built two tokeners and regrew their buffers, 27 allocator calls. Every tokener now goes back, its buffer counted as kept (§6) and freed under memory pressure (§5, Relief).
- **Slices.** A slice is at most 16 KiB and 256 values. The scanner finds where it ends, before the value that would be one too many, or before a split character. A body that fits the step's remaining share is parsed at once, so cheap requests are answered in their own step.
- **Members.** The pre-scanner also counts members per object (`--max-members`, 1024). When an object grows, json-c rehashes its whole table in one call: 116 k keys made 11 ms steps, while 1024 members cost under 0.1 ms.
- **Numbers** (review of S2b). json-c converts a number whole when it ends, strtod over all its digits: a 1 MB number took a 1.9 ms step, 16 MB 16 ms. The pre-scanner limits numbers and literals to 1 KiB (400), and so does the parse of an answer; no valid one needs more.
- **Copies** (review of S2b). json-c also copies a string whole when it ends, about 0.4–0.5 ms per MiB, which no slice can split. It counts in full as `copy` work, bound 1 MiB, which the default body limit keeps to; a raised `--max-body` shows in the statistics as a step over the bound.
- **Answers** (review of S2b). The upstream's answer is parsed like a body, a slice a step, and checked to be UTF-8 slice by slice, since json-c lets overlong forms through; its text is read in a step of its own, and the tree freed in slices. A 16 MB answer took one 36 ms step; now its two whole copies, json-c's and the text's, take a few ms each. Answers stay capped at 16 MiB until S6's 1 MiB cap (§4), so one over 1 MiB still breaks the copy bound, and the statistics show it.
- **Freeing.** Freeing is sliced too: 256 values a bulk step, each container taken apart from its last element or first member in O(1). Each request frees its own message after its reply has gone out, and ends its stream only then. Its connection's next request waits, so message memory is bounded by the requests under way. With one shared freeing entry, several dense clients outran it: RSS reached 2.3 GB. A parse that fails or loses its client hands json-c's unfinished containers to the same slices. This reads two tokener fields json-c documents as private.
- **Memory.** glibc keeps freed small chunks, so until S3m askai called `malloc_trim(0)` when a turn was quiet, checked every 5 s; since S3m it trims only to relieve memory pressure (above). The call can be neither split nor moved off the loop. Its cost is the release of pages, about 50 µs per MB. Trimming after every few hundred values freed cost up to 1.6 ms a call on the heap dense bodies leave, as each call walks its ~5000 free chunks again. A trimming thread would hold the loop's arena lock as long. So after a burst of large trees the trim takes one step: 16–22 ms after the dense and check profiles, which free 280–330 MB, and 53–67 ms beside 32 CPU hogs. Since the review of S2b the harness shows that step (§8), within the gross-outlier limit. jemalloc with background purging released the memory off the loop, but kept about 5 MB more and had turns of 9–11 ms under load; mimalloc purged in a 19.8 ms step. The allocator stays open (risk 6). json-c takes ~0.65 KiB for an empty object: raising `--max-values` raises memory per request accordingly.
- **`mcp_static`** came in S2b rather than S4. Replies are built from fragments: the static ones, and per-request ids, messages and answers, escaped 64 KiB a step. The upstream request deep-copies what it takes of the configuration (temperature, `--extra`), where it took references at first: their counts are not atomic, and with N loops two requests would race on them (review of S2b).

### Future: buffer thrift store

The user's planned evolution of the stash; not built. A lock-free ring buffer stashes pointers to previously allocated buffers of varying sizes, for all threads. A thread that does not anticipate a momentary need for more buffer space uses idle cycles to donate its larger buffer to the store and grab a more economically sized one, in a single atomic operation that may fail, in which case it keeps its large buffer. A lower-priority background thread releases memory from the store over time, when it is determined that other processes need memory more than the store needs "a stockpile of expensive shoes". The stash stays compatible with it: its blocks are plain allocations of a class's size, which any thread may free or store, and a `struct buf` carries its storage's size, and a stash's count of what its buffers hold allows for blocks that came from another thread. A stash would offer the store its surplus, which it now gives the allocator under pressure, and look there on a miss before the allocator.

## 6. Failure, shutdown, logging, metrics

**Isolation.** Callbacks return `void`, and an error closes only its own connection or job. `loop_fatal()` is for broken invariants; today any callback or curl error ends the daemon (loop.c:146-147, http.c:86 [T]). Out-of-memory gets a 503.

**Shutdown.** Signals are blocked before `pthread_create`; the brainstem reads a signalfd. Thread start is a monotonic-clock handshake that propagates errors [M]. On SIGTERM, home closes the listener and posts each loop's pre-allocated `drain`; loops close idle connections, cancel queued jobs, end SSE with an error event and give running work 5 s; the brainstem joins the loops, the blockers, then the logger. A second signal exits at once. No `pthread_cancel`.

*As built in S3* (`brainstem.h`): before any thread starts, the brainstem blocks every asynchronous signal, so threads inherit the mask; it then takes SIGINT, SIGTERM, SIGHUP, SIGUSR1 (statistics) and, with `--test-stall`, SIGUSR2 through its signalfd, and leaves the rest to their default actions on itself. Of the first three, one that the process started with ignored, as nohup and a shell's background job leave them, stays ignored and out of the signalfd, which would take it all the same: Linux keeps a blocked signal pending whatever its action (review of S3: `nohup askai` ended on SIGHUP). Each thread reports its start, or its error, through an atomic word and the brainstem's eventfd, which the brainstem waits on with `ppoll` against a monotonic deadline (10 s); it never takes a lock a loop holds nor waits for a loop. The first SIGINT, SIGTERM or SIGHUP (SIGHUP until S7's reload) orders the loop to drain within the grace period (`--grace`, 5 s):
- the listener closes and idle connections close; a request under way finishes, its body included, and its response says `Connection: close`; a connection between requests ends rather than begin another, one part way through a head when it next sends or at the deadline;
- a tool call waiting for the upstream, or not yet sent there, ends at once with a JSON-RPC error, on an event stream as its last event, and its upstream request is cancelled. Giving it the grace period would rarely let it finish, as answers take seconds to minutes; the client learns at once. S6's scheduler may refine this with progress;
- connections left at four fifths of the grace period close; the loop exits once none is left.

The order to drain only flags and queues: bulk steps close idle connections, and at the deadline every one left, 32 a step (`closes`), and end tool calls 8 a step (`reqs`). The first version did all of it in the order's handler, one turn for the whole drain: 50–100 ms for 10 000 idle connections, 250–500 ms for 40 000 (review of S3).

The brainstem then joins the loop, stops the blockers (2 s at most: a blocker stuck in a call is left to the process's exit, its loop kept for it), and gives the logger 1 s to write what it holds; exit status 0. A second signal, the grace period running out, or the loop found in one turn for 1 s while it should drain, ends the process at once with status 3, after the logger has had up to 1 s; signals then go unread. Teardown after the loop's last turn is no turn to the watchdog, which saw a slow `curl_multi_cleanup` as a stuck loop (review of S3).

*As built in S4*, with home: the brainstem starts home, then the client loop; the order to drain goes to both. The client loop drains as in S3: its tool calls end with the JSON-RPC error and set CANCEL. Home cancels the jobs in flight, eight a step (`reqs`), each completing as cancelled, and ends a job submitted from then on at once. The client loop exits once its connections are gone; the brainstem joins it and tells home it is alone (an order bit, ALONE), and home exits once no job is in flight. The brainstem joins home, stops the blockers, which post to home, and frees home's loop and then the client loop's, each handling what its inbox still holds: home's ends any job left, whose completion goes to the client loop's, which frees what comes back. A loop that exits on its own starts the same shutdown. The forced exits are S3's for either loop: a second signal, the grace period, or either loop stuck in one turn for 1 s while draining (status 3). With `--test-stall`, SIGUSR2 holds both loops.

*As built in S5*, with N client loops: the brainstem starts home, then the client loops one after another, each through the start handshake with every signal blocked, and once all run orders home to open its door (§3). The order to drain goes to home and to every client loop. Home closes the listener first and places no more, and drains its jobs as in S4; the client loops drain as in S4, a client loop closing at once, and giving back, a connection home places as it drains. The brainstem joins the client loops as they exit, in any order; then it tells home it is alone (ALONE), joins it, and stops the blockers. Then it finishes the loops, home's first: what home's inbox still holds, jobs whose fronts are client loops and connections given back, posts only to client loops, which are not finished yet, and frees the connections; then each client loop's, whose handlers post to nobody: a connection home handed over but the loop never took is closed and its storage freed, a job's completion or return frees the job. So no message is posted to or handled by a finished loop. Every per-loop object another loop reads, such as its metrics, lasts until all are finished (the first version freed a client loop's MCP counts as it stopped, while another rendered them: ThreadSanitizer and AddressSanitizer both found it). A client loop that exits on its own, or fails to start, any of the N, part way through starting them, starts the same shutdown, those already running draining; so does home that fails to start, its listener included, as in S4 (§3). The brainstem's join of a loop that exited on its own starts it too, should the join see the exit first (review of S5: a join between two looks let one such exit go unnoticed), and out of memory for the loops' threads askai exits 1 (review of S5: it crashed). The forced exits are S3's for every loop: a second signal, the grace period, or any loop stuck in one turn for 1 s while draining (status 3). With `--test-stall`, SIGUSR2 holds every loop.

**Reload.** On SIGHUP a blocker reads the files and home posts a new `SSL_CTX` and config; old ones live on by refcount. *Moved to S7* (decided in S5): askai reads no files, as its configuration is the command line and the environment, so there is nothing to reload until S7's configuration file (the certificates follow with TLS in S9); SIGHUP drains until then. The configuration and `mcp_static` stay immutable, published before any loop starts (R5).

**Logging.** Per-thread 256 KiB SPSC rings of preformatted records; a full ring drops and counts. Per-call-site rate limits; disabled levels skip argument evaluation [S]. The logger is woken through the same asleep-gated eventfd and is the only thread that blocks on stderr (`writev`).

*As built in S3* (`log.h`): `LOG(level, …)` formats a whole line of up to 1 KiB on the caller's stack and copies it into the caller's ring, or drops it and counts it; a call site logs at most 32 lines a second, and its next line says how many it held back. `-v` enables the verbose level; levels above it skip the call. The logger writes the rings round-robin with one `writev`, waits in `poll` for room on a non-blocking stderr, and blocks on a blocking one; it reports drops once it can write again. It is detached, and once it says it is done it touches nothing shared but the brainstem's eventfd, so no exit path waits for it beyond its bound. A thread that finds no ring left drops its lines, counted, rather than write stderr itself; the brainstem sizes the rings by its threads. Every line askai wrote to stderr goes through it, but for errors in the options, before it starts.

**Metrics.** Per-thread log-linear histograms (relaxed atomics) at `GET /metrics` (loopback or token) and a `status` tool: turn and step time, inbox delay, timer lateness, per-method latency, handshake CPU, job wait / time to first token / run time, drops, MODs.

*As built in S3* (`metrics.h`, `hist.h`): every histogram and gauge has one writer, which updates it with relaxed loads and stores, as cheap as plain ones, and so do most counters; those of log lines and blocker jobs, which several threads add to, are atomic sums of rare events; readers use relaxed loads. `GET /metrics` gives Prometheus's text format: per loop, turn and step times, timer lateness, inbox delay and the most of each unit of work a step did; request times by MCP method; upstream wait (its host lookup included) and run times; host lookups; blocker jobs; log lines, drops and held-back lines; watchdog reports and late wakes; resident memory, descriptors and their limit, and PSI where the kernel has it. Histograms have buckets from 1 µs to 300 s. A request renders at most 32 cost units a bulk step, a histogram costing 8, then answers with the whole text (about 26 KB). The transport marks a stream trusted when the client showed the token or, none being set, is on loopback and names no other host than localhost, 127.0.0.1 or [::1] in `Host`; others get 403. A page whose name an attacker rebinds to 127.0.0.1 sends no Origin with a same-origin GET, but names its own host (review of S3). The `status` tool, handshake CPU (S9), time to first token (S6) and MOD counts are not built yet. The SIGUSR1 statistics are unchanged: windows between reports, kept beside the metrics. From S3m, memory pressure, each input's level and the inputs (resident memory and its threshold, RAM and what is available, the cgroup's use and limit where it has one), and per loop the stash's retained bytes, hits and misses, the requests kept for reuse and the bytes they and the pooled tokeners hold, and the bytes, reliefs and trims of relieving pressure (§5). From S4 each loop's series carry its name, `loop="1"` or `loop="home"`; home's jobs, submitted, in flight, and ended as completed, cancelled or rejected; per client loop the calls it cancelled while their job ran, the completions it dropped for want of their call, and the jobs it keeps for reuse; the upstream's wait and run times and lookups are home's. From S5 the client loops' series carry `loop="1"` to `loop="N"`, home's `loop="home"`, last; the request times by method are each client loop's, as are its connections (`askai_connections`) and the connections home placed on it (`askai_connections_placed_total`). A render still takes at most 32 cost units a bulk step however large N is: a series that is no loop's is visited once, not once a loop, and a loop's family begins with client loop 1, which has every series, so no step looks back over the loops. SIGUSR1's lines name their loop: `stats loop1 turn …` to `stats loopN …`, and `stats home …`. From S6 home's scheduler and upstream: the jobs queued and the principals with jobs queued, the jobs started, the upstream calls under way and the slots, the calls cancelled upstream once their request had gone, streamed answers' chunks and stalls, and the breaker's state, opens and probes; nothing a principal, as their number has no bound. From S6m the man tool's manual, when askai offers it: the pages kept and their bytes, the calls a kept page answered and those that waited, and the runs of man to find a file and to render a page.

**Watchdog.** It runs on the logger rather than home, since home is the likeliest to stall [J2]. It flags any loop that has been inside one turn for more than 20 ms (`turn_start` set, not asleep), unless its own wake was late [S].

*As built in S3*, it runs on the brainstem (§11.1), which, unlike the logger, never blocks on stderr. Each loop stores, with relaxed atomics, when its turn began, and 0 while it waits for events. Every half threshold (`--watchdog`, 20 ms) the brainstem reports a turn longer than the threshold, once per turn, through a rate-limited line and a counter: a diagnostic, not a gate. Woken more than a threshold late, it was held up itself, likely with the rest of the process or the machine, so it vouches only for the time since then: SIGSTOP of the whole process, as the harness's stall check does, reports nothing. Its own resource sample does not count as lateness: counting 100 000 descriptors took tens of ms, which made every second's look late, so that a loop stuck while draining ran into the grace period instead (review of S3). The sample reads `/proc/self/fd` with `getdents64` into a buffer on its stack, as `opendir` would `malloc` in the main arena, whose lock the loop's `malloc_trim` takes.

## 8. Proof: bounded work, shared degradation

**Policy** (from the user, at S2b). The daemon will not run on a brand-new number cruncher. It will share busy or slow machines, and when the machine struggles, its connections should share the struggle. So no absolute latency target is a gate. Absolute latencies are measured and reported as information. A run fails only on:
- errors;
- lockouts;
- leaks;
- limits or deadlines not enforced;
- unfairness;
- unbounded work;
- gross outliers relative to the same machine's idle baseline, measured in the same run.

Bounded work per turn stays mandatory, but it is checked in units of work (§1).

The reasons were plain in S2a's records. An absolute bound measures the machine as much as the daemon: S2a's one turn over 1 ms in nineteen storms came from the desktop preempting askai, while askai's own steps stayed under 0.65 ms. A fast machine can also meet a latency target while one client starves, which is the failure that matters to users. S0's lockout, where every fresh connection timed out while the others answered in 37 µs, is such a starvation. So is S2a's review finding of step-queued work waiting 5 s behind callback work.

**Harness** (`tests/load/`, C, grown from [T] probe.c and [M] load.c):
- an open-loop Poisson probe (ping, tools/list at 1 kHz) timed from the *scheduled* send, so coordinated omission cannot hide stalls [ws]; its keep-alive connections take the arrivals in turn, each queueing its own, so one held back builds up latency rather than shedding arrivals to the others;
- modes idle, jobs, loris, slow body, slow reader, pipeline, malformed, churn and hostile JSON; from S2b also dense JSON (1 MiB bodies of many small values), tool calls that hang up on their event stream, and large answers (512 KiB); from S4 tool calls that hang up about when their answer comes (`race`); the heavy modes (pipeline, malformed, hostile, dense) time each batch or body;
- a C upstream mock with slots, token rate, SSE and cancel counting;
- ws.c in `tests/bench/`.

A run has up to four phases on one daemon: the probe alone, as the idle baseline; the heavy modes alone, a few rounds each, as theirs; the profile's load with the probe; and the probe alone again, for as long as the load while the daemon keeps the load's memory for reuse, then under critical memory pressure, which the harness induces (from S3m), until the daemon has given that memory back.

| Clause | A run fails on |
|---|---|
| errors | a crash or non-zero exit of the daemon, generator or mock; a probe arrival failed, timed out or lost, in any phase; a background request unanswered; a tool call failed or cut off; mock counters that do not add up |
| lockout | a fresh connection not served (fresh-connection probe, churn) |
| limits | loris and slow-body clients open past their deadline; an upstream call outliving its client |
| leaks | descriptors not back at idle + 2, or RSS not within 4 MiB of idle, by the end of the after phase, whose memory pressure has the daemon give back what it kept |
| fairness | a probe connection's p90 over 10× the median connection's; a probe kind's p90 over 10× the median kind's; a tool-call connection with no call done while the median one did 3; a heavy mode's p90 over 50× its p90 alone, or none done |
| work | a unit of work in a step over its bound, on any loop, unsplittable work counting in full (§1) |
| jobs | from S4, home's jobs at exit not submitted = completed + cancelled + rejected, or more upstream cancels than cancelled jobs; from S6, once the load's calls have ended and before the daemon stops, a job in flight or an upstream request under way or queued, more upstream cancels than calls askai cancelled upstream once their request had gone, or fewer by over 10 and 5 % of them, and in `sse` not as many |
| scheduler | from S6, in `flood`: an interactive session that completed under `FAIR_SHARE` (0.5) of its fair share of calls, the calls the run completed shared among the sessions and the flooder, or whose calls' p90 waited over `FAIR_WAIT` (4) service times beyond their own |
| outliers | probe p99 in the load or the after phase over 100× the idle p99; a turn in either over 1000× the idle p99 turn and over 100× the idle probe p99 |

Fairness uses the p90 because a starved client is slow throughout, while a machine hiccup hits every client alike and reaches one client's p99 only when a few land on it. All the factors are generous on purpose. A starved client shows thousands of times its peers' latency (S0's lockout: 5 s against 37 µs), while sharing shows 1–2× (S2b storm: 1.1–1.2× on connections, 1.6–1.7× on kinds). Heavy work yields to cheap requests by design, so its factor is the larger; it shows 1.0–10.4× its time alone. The factors are environment variables of `run.sh`.

*From the review of S2b* (`doc/core-measurements.md`), the harness itself was found to hide two things. The fairness check left out probe connections with under 50 samples, and a connection held back took fewer arrivals, so it was the one left out: one answering in 300 ms beside peers at 75 µs passed. And the loop's statistics were taken before a trim that followed the load, 14–19 ms after dense bodies. Hence the per-connection turns, the solo and after phases, and the counting of unsplittable work in full.

**Reported, not judged:** probe p50/p99/p99.9/max and their ratios to the idle phase; turn and step times; timer lateness; inbox delay, in `/metrics` from S3. The former targets remain a reference for a quiet modern desktop, and S0–S2a were judged by them:
- cheap-request RTT p99 ≤ 250 µs, p99.9 ≤ 1 ms, max ≤ 5 ms;
- turn p99.9 ≤ 1 ms, max ≤ 2 ms;
- inbox and timer p99 ≤ 20 / 50 µs.

One loop already reaches p99 37 µs, with max under 90 µs at 3000 calls in flight [T].

**Storm run** (all at once; NDEBUG, unpinned, worst of 3): 10k idle connections; 1000 tool calls from 250 principals on 1 slot; 64 each of loris, slow-body and slow-reader clients; a 4 MiB pipeline; 1000 connections/s of churn; from S9, 200 TLS handshakes/s; from S8, saturating tasks.

**Gates** beyond the table: submitted = completed + cancelled + rejected; upstream cancels = disconnects; stalled stderr harmless (S3). From S4 the harness checks the first at askai's exit and that the upstream saw no more cancels than askai cancelled jobs (the `jobs` clause); the second holds where every hang-up reaches the upstream in time (`sse`: every call the upstream saw, it saw cancelled), a job cancelled before it was sent never reaches the upstream, and a race may see a job cancelled after the upstream's answer has gone out.

*From S6* the mock serves llama-server's `GET /props` with its slots, streams its answers at its token rate, or unpaced 256 tokens an event, and counts the hang-ups of streams under way, and of requests that come with their hang-up, as cancelled; the generator's tool-call connections come each from an address of its own, so that each is a principal of its own (one address's 64 calls would be refused past eight queued), and two more modes: a flooder's many calls in one session, which call again 10 ms after a busy refusal, and interactive sessions' one call at a time, each call timed. The `flood` profile has 16 flooding connections and 4 interactive sessions against a mock of 2 slots, streaming 20 tokens at 100 a second: a service time of 200 ms. The fair share of an interactive session is the calls the run completed shared among the sessions and the flooder, a call at a time at most (review of S6: the slots' nominal capacity, 2 slots over 200 ms, which the runs passed by a tenth, overstated the share the sessions got); with `ASKAI_ARGS=--test-fifo` the same load shows first in first out. The `jobs` clause holds the upstream's cancels to the calls askai cancelled upstream once their request had gone, both read once the load's calls have ended while the daemon still runs, when neither may have a call under way: the counts at exit came after the daemon's exit had closed every upstream connection, which the mock counted as cancelled, so a call that outlived its job passed (review of S6). A call cancelled before its request went never reaches the upstream, and one cancelled as its answer finished is the mock's served, so the upstream sees no more, and no fewer by more than 10 and 5 %; in `sse`, whose answers now stream for 60 s, longer than the run, no hang-up races an answer, and it sees as many. The mock sets `TCP_NODELAY`, as the generator does: a streamed answer's head, events and tail are sends of their own, which Nagle held back for askai's delayed ACKs, some 40 ms a call (review of S6). `race` and `cancel`, whose mock has unlimited slots, give askai `--slots 64`, so that their hang-ups race the answers, as before, rather than end calls in the queue.

*From S5* the harness reads every loop's statistics, each line naming its loop, and judges each: the `work` clause on home and every client loop, the `outliers` clause on the longest turn of any, against the most of the client loops' idle p99 turns. It reports how many connections home placed on each client loop (`PLACE`, the least, the median and the most, from `GET /metrics`), takes more options for askai (`ASKAI_ARGS`, such as `--loops`), allows each client loop 256 KiB more resident memory in the `leaks` clause, for glibc's per-thread cache (§5), and has a `cancel` profile, of legacy tool calls cancelled by `notifications/cancelled` on connections of their own, about when their answers come.

**CI.** `make check` includes `check-load`: the verdict on a light mix of every mode, 2 s idle, the heavy modes alone, 5 s of load and 5 s after, about 15 s in all (17–19 s on a loaded machine). Since the review of S2b it passed the campaign's five runs on a busy desktop and six beside 32 CPU hogs (load average up to 39). Beside the hogs the trim after the load took 53–67 ms, within the outlier limit only through its arm of 100× the idle probe p99, which the hogs slowed as well. `make load` runs the storm under the same verdict. ASan/UBSan run `tests/askai.py`, and TSan from S3, when threads came (it found mcp2210's races in under 2 s [M]); each also runs a load profile.

## 10. Risks and open decisions

**Decided.** Busy jobs get `isError: true` with a retry hint (the calling model sees a tool outcome); transport overload gets 503 + Retry-After. RDHUP cancels in every era. With `-np 1`, preemption is on, at most once per job (*S6:* deferred with classes to S8, as every call is interactive until tasks). Hybrid PQ stays on (+55 µs fits a step). LT, the fd BIO and the single acceptor change only on measurement. "No pool" gave way to the user's memory directive at S3m (§5, §11.6). *S6* (§4): a job's principal is its call's MCP session, else its client's address; S is `--slots`, else llama-server's `/props` `total_slots` for every protocol but `gemini` and a host that is no well-known cloud API, else 4, and libcurl's cache follows it; deficit round-robin costs a job; a principal may have eight queued, and a job that a free slot takes at once queues for none; `--timeout` bounds the wait in the queue from submission and the upstream call from its start, and `--chunk-timeout` (60 s) a pause once the answer has begun; streaming is forced, and a plain answer is parsed as before; the breaker counts transfer errors, timeouts, stalls, 5xx and 429, opens after five in a row or at once for an answer's `Retry-After`, ends the jobs queued as it opens, and backs off from a second, doubling to a minute.

**Risks.**
1. Steps are a convention: a slow library call stalls its loop. Overrun histograms and asserts catch it; unproven calls go to the blocker.
2. Placement weights are guesses until S5/S8; fallback is migrating idle keep-alive connections. *S5:* measured, not migrated. Connections + a quarter of the utilisation in per mille, with the utilisation sampled over a second at least and each connection placed since counting once more, kept a storm's 10 000 idle connections and its churn within 1.6 times of each other over 32 loops (the heaviest loop being the pipeline's), and a churn-only load closer (doc/core-measurements.md); a utilisation sampled every 10 ms let one request's millisecond weigh more than a connection, and without the placements since, churn went to the lightest loops by rank, 14.7 times as many to the lightest as to the heaviest. The weights stay open for S8's tasks, whose work the utilisation does not foresee.
3. Home saturation: the scheduler is message-only, and from S4 home is a loop of its own (§11.1), whose turns the watchdog and the harness watch.
4. JSON figures are warm best-case [J1]; S2's overrun data sets the cap.
5. Co-located CPU load: an equal-priority hog pushed loop p99 to 2.2 ms [ws]. Options: `CPUWeight=`, or an isolation mode where loops run no tasks. Under §8's policy this is a shared slowdown, not a failure, as long as it stays shared: `check-load` beside 32 hogs saw 13–66× the idle p50 and connection p90 spreads of 1.05–1.19.
6. glibc arenas may fragment. What askai keeps is its working set's peak, the stash's share within twice it, until memory pressure, and giving it back ends in one call that no step can share (§5): 18–22 ms after the check profile's ~350 MB, 53–67 ms on a loaded machine (S2b), now only under pressure. Keeping it leans on glibc's tuning and internals (§5: a thread arena's top is trimmed only by a large free; a thread's heap that empties is deleted). jemalloc with background purging and mimalloc were measured at the review of S2b (§5); neither is adopted, and the choice stays open.
7. More than 256 CPUs overflow the 8-bit loop field. *S5:* N is capped at 255 client loops, home being 0, and `--loops` takes at most 255; a larger machine runs 255. Widening the field would take from the slot or generation bits.
8. io_uring (+8 %) is blocked by Docker and RHEL [P]; it stays an optional later backend.
9. **Principals by session** (S6). A session is whatever `Mcp-Session-Id` a client sends, so one client may open many sessions and take a share for each. The per-address connection cap (256) bounds them, as each call holds a connection; `--max-calls` bounds the jobs in flight. Not solved now; sessions of one address could share a principal's share, as hierarchical fair queuing would, should it matter.
10. **A job's cost** (S6). The scheduler gives each principal a job a round, not a share of slot time: a principal whose calls generate longer answers takes more of the slots. `--max-tokens` and the deadline bound a job's slot time; charging it, once known, would need deficits that stay O(1) to find a principal that may start (§4). A round has only the principals with jobs queued, so with S > 1 a principal that keeps jobs queued takes a slot whenever one frees while a principal of one call at a time has yet to send its next: in `flood` the flooder completed about twice an interactive session's calls (measurements, S6).

## 11. Revisions after review

Notes from the review of this design, to settle at the stages they affect:

1. **Loop 0 carries too much** (settle before S4/S5). Listener, LLM scheduler, job registry, children and configuration may move onto one or two high-importance "sidekick" threads. The main thread should rather be concerned with the hardware and the operating system the service runs on: a brainstem that still catches a Ctrl-C when the cortex has gone fishing. Signal handling, the watchdog and resource monitoring are natural tenants.

   **Resolved for S3.** The main thread is the brainstem (§1, §6): it owns the signalfd, the process's lifecycle (the start handshake, shutdown), the watchdog and a resource monitor (resident memory, descriptors against RLIMIT_NOFILE, PSI where present, sampled each second, exposed as metrics, logged when over or back under a threshold). It never takes a lock a loop holds nor waits for a loop or the logger beyond a bound, so it ends the process when the loop is stuck. The event loop runs on a thread of its own, which the brainstem starts and stops; the logger is the first sidekick thread. **Left for S4/S5:** with N loops, whether the listener, LLM scheduler, job registry, children and configuration stay on loop 0 or move to one or two sidekicks; draining N loops, and reload on SIGHUP (S5); the resource thresholds' effect on admission, which only logs for now. The review of S3 kept the brainstem's periodic work free of `malloc`, and its forced exits from spinning on unread signals or leaving finished threads unjoined.
   **Resolved for S4.** Home is a sidekick thread of its own, not loop 0 (§1): the brainstem starts it before the client loop and stops it after. It runs its own loop and serves no client, and owns the curl bridge (the multi, its timers, host lookups through the blockers), the job registry and a minimal scheduler: admission, with a cap on the jobs in flight beyond which a call is answered at once as busy, a tool error with a retry hint (§10), and first-in first-out starts. Client loop 1 keeps the listener, its connections, httpd, MCP and its call slots, and parses answers. Children (S8) and configuration and `SSL_CTX` (S5, S7) are to live on home. **Left for S5:** N client loops, and whether they number N or N − 1 beside home; where accept runs and how connections are placed; the legacy (session, requestId) cancel lookup, which moves to home's registry; draining N loops; reload on SIGHUP; ordering one trim once every loop has released (§5), where S4's loops take turns and leave out a walk of the arenas that another's covers.
   **Resolved for S5.** N client loops serve the clients, home beside them (§1, with the measurements behind N); home accepts them and places each on the lighter of two client loops, and counts each loop's and each client address's connections, from placement to give-back (§3); the limits that hold for the process live where each is decided without a lock, an O(n) walk or a round trip (§3's table); the legacy (session, requestId) cancellation goes through home's registry, O(1) (§4); the drain reaches home and every client loop, and the loops are finished home first, so no message reaches a finished loop (§6); a relief of memory pressure ends in one trim, its walk of the arenas on a blocker (§5). Reload on SIGHUP moved to S7: askai reads no files, its configuration being the command line and the environment, so there is nothing to reload until S7's certificates; SIGHUP drains until then, and the configuration and `mcp_static` stay immutable, published before start (R5). **Left for S6 and later:** the scheduler's principals, classes and breaker, streaming, progress and the 1 MiB answer cap (S6), which libcurl's cache of idle upstream connections also waits on; `SSL_CTX`, handshakes as steps, and reload (S7); tasks, their placement and re-placement, which may reuse home's view of the client loops' utilisation, and children (S8); migrating idle connections, should placement prove poor (risk 2); a global order of eviction under descriptor pressure, which with several loops is as near least recently used as the loops tell home (§3); bounding what N loops keep in N arenas but by memory pressure, and the tcache each keeps (§5), with the allocator still open (risk 6); the resource thresholds' effect on admission.
   **Resolved for S6.** Home's scheduler has principals, the call's MCP session or else its client's address, eight jobs queued each at most, and deficit round-robin across them at a job a round over S slots, S from `--slots`, llama-server's `/props` or 4, which libcurl's connection cache follows; every protocol streams its answer, whose events home reads a share a step into its text, with a 60 s chunk timeout once it has begun and the deadline from the start upstream (the wait in the queue bounded apart, from submission); one breaker on the upstream; progress for calls with a `progressToken`, on their event streams (§4). The 16 MiB answer cap stays, now of the text. **Left for S7 and later:** `SSL_CTX`, handshakes as steps, and reload (S7); classes, the slot reserved for interactive work and preemption, with tasks, their placement and re-placement, and children (S8); a principal's share for the sessions of one client (risk 9) and a cost by slot time (risk 10), should they matter; and the items left from S5 but those S6 resolved. *Revised after S6* (with the user, after S6's first run against a real llama-server): S7 takes the configuration file, identity and roles, which every tool and policy waits on, and reload with them; TLS (`SSL_CTX`, handshakes as steps) moves to S9, as users may reach askai over ssh, or through a proxy that ends TLS, until then.
2. **Client loops are their own thing** (confirmed): loops that own client connections do not double as the home of shared services.
3. **Request body limit** (S2): 1 MiB is the bare minimum; users may push far more during an information-gathering session. The limit is a tunable that starts at 1 MiB.
4. **Order** (confirmed): the foundation first, S0 onwards.
5. **Latency policy** (from the user, at S2b; binding from then on): absolute latency targets are not gates. Latencies are reported. Runs fail on errors, lockouts, leaks, limits not enforced, unfairness, unbounded work in work units, and gross outliers relative to the same run's idle baseline (§8). The reason is the target machine: shared, busy or slow, where connections should share any struggle rather than some of them meet a number.
6. **Memory retention** (from the user, at S3m; it supersedes trimming when idle, §5): freeing and allocating every loop turn, or a little less often, is not wanted; `struct buf` and dstr exist for this among other things. Threads hold on to their working buffer space, and actively free some of the accumulated surplus only when a memory pressure mechanism, such as a process-wide absolute threshold or a system-wide relative watchdog, determines it is time for preventative action. Built as per-loop stashes and the brainstem's pressure levels (§5); the planned evolution is the thrift store (§5).
