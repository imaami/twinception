# twinception

Experimental C23 client for paired LLM inference.  The ordinary mode
crosses complete reasoning traces between turns.  Rapid mode goes further: the
models generate short reasoning quanta in lockstep, and each model's next
inference is conditioned on the *other* model's accumulated reasoning rather
than its own.

The program uses libcurl's multi-socket interface with epoll/timerfd; there are
no HTTP worker threads or polling loops.

## Dependencies

- C23 compiler
- libcurl
- json-c
- Linux epoll + timerfd

## Build

```sh
make
make check
```

## Ordinary whole-turn swapping

Run two current llama.cpp `llama-server` instances on separate ports, then:

```sh
./twinception -d
```

Both receive each human prompt.  In the default `split` history mode, after a
completed turn:

```text
A history: answer_A + reasoning_B
B history: answer_B + reasoning_A
```

`-H shared-a` and `-H shared-b` instead force the visible assistant content in
both histories to come from one selected model while retaining crossed
reasoning.

Before inference, twinception uses `/apply-template` to verify that the
immediately preceding `reasoning_content` actually survives the model's chat
template.  If older historical reasoning is pruned it warns but continues.  A
template that drops the latest reasoning is rejected.  `-P` disables this check
for a non-llama proxy when its behavior has been verified separately.

## Causal rapid swapping

```sh
./twinception -q 32 -R 512 -n 2048 -d
```

`-q N` enables rapid mode and sets the maximum number of generated tokens per
reasoning quantum.  `-R N` caps the total rapid reasoning generated by each
model in one turn; it defaults to 512 when `-q` is present.  `-n` becomes the
final-answer token cap.

For each user turn, twinception first asks `/apply-template` for each local
llama.cpp model's native prompt.  At startup it has already compared a user-only generation prompt
with a synthetic completed assistant turn, so it knows both the model-specific
generation-to-reasoning prefix and the reasoning-to-answer transition.  It
replaces/prefills the former before using llama.cpp's raw `/completion` endpoint
with `cache_prompt=true`:

```text
round 0:  A sees base_A                 B sees base_B
           emits a0                      emits b0

round 1:  A sees base_A + b0            B sees base_B + a0
           emits a1                      emits b1

round 2:  A sees base_A + b0+b1         B sees base_B + a0+a1
           ...                           ...
```

A model's own emitted reasoning is never appended to its next prompt.  The
plain text is crossed; each destination server tokenizes it with its own
vocabulary.

Rapid mode therefore makes two startup `/apply-template` probes per model.  A
user-only render identifies the ordinary generation tail; a synthetic completed
assistant turn contains a reasoning sentinel followed by an answer sentinel.
Their differing tails identify the native reasoning-entry prefix, while the
bytes between the two sentinels identify the reasoning-to-answer transition.
This matters for Harmony/GPT-OSS: raw generation would otherwise begin with
`<|channel|>analysis<|message|>`, which is protocol syntax rather than reasoning
payload.  Twinception now prefills that syntax itself, so it is never crossed or
stored as thought.

After the rapid reasoning budget (or an early reasoning stop), the native
reasoning-to-answer transition is appended to each destination prompt and a
final `/completion` is requested.  Consequently rapid mode does not require old
reasoning traces to survive historical chat-template rendering, but it does
require llama.cpp-compatible `/apply-template` and `/completion` endpoints on
each local side.  `-P` is therefore invalid with `-q` when either provider is
llama.cpp; an all-DeepInfra rapid run has no template probe to skip.

Small quanta increase causal coupling but also increase HTTP/task scheduling
and prompt-suffix processing overhead.  `16` or `32` is a sensible first test;
`64` is a useful comparison point.  Use a dedicated server slot (`-np 1`) for
each model when measuring cache behavior.

## Crosstalk

`-C N` adds N autonomous rounds after each human/seed turn.  The visible answers
are crossed as the next user inputs:

```text
next A user <- previous B answer
next B user <- previous A answer
```

For example:

```sh
./twinception -C 20 -p 'You may now address the other participant.' -d
```

`-C -1` runs without a round limit.  `:stop` prevents another autonomous round
after the current pair finishes; `:quit` also exits once the in-flight pair has
completed.  `split` is the least confounded history mode for ordinary dialogue;
using `shared-a`/`shared-b` with crosstalk is allowed and intentionally produces
stranger autobiographical histories.

Rapid swapping and crosstalk can be combined:

```sh
./twinception -q 32 -R 512 -n 1024 -C 10 -d \
  -p 'You may now address the other participant.'
```

A paired turn is transactional in both modes.  If either backend fails, neither
history advances and autonomous crosstalk is stopped.

## DeepInfra

Either side can use DeepInfra instead of llama.cpp.  `Qwen/Qwen3.6-35B-A3B`
is the default hosted model.  Ordinary turns use DeepInfra's OpenAI-compatible
reasoning stream; crossed historical thought is replayed as
`reasoning_content`, with Qwen `preserve_thinking` explicitly enabled through
`chat_template_kwargs`.

Set the API key in the environment rather than putting it on the command line:

```sh
export DEEPINFRA_API_KEY='...'
```

`DEEPINFRA_TOKEN` is accepted as an alias because DeepInfra's documentation uses
both names in examples.

For two DeepInfra-hosted models:

```sh
./twinception --a-provider deepinfra --b-provider deepinfra -d
```

For one local llama.cpp model and one DeepInfra model:

```sh
./twinception --b-provider deepinfra -d
```

`-A`/`-B` override the DeepInfra model ID, and `-a`/`-b` can override the API
URL.  The default endpoint is
`https://api.deepinfra.com/v1/openai/chat/completions`.  DeepInfra automatically
caches repeated prompt prefixes, which is useful for rapid mode.

DeepInfra does not expose a documented raw reasoning-format extension.  Rapid mode
therefore uses the documented assistant-continuation behavior instead: it sets
`continue_final_message=true` and prefills a Qwen reasoning response with the
other model's accumulated trace.

```text
round 0:  assistant prefill = <think>\n
round 1:  assistant prefill = <think>\n + foreign quantum 0
...
answer:   assistant prefill = <think>\n + foreign trace + </think>\n
```

Thinking quanta stop on `</think>`.  DeepInfra may return the continued thought
as `delta.reasoning_content` or as raw `delta.content`; Twinception accepts both
for the thinking phase, but only ordinary `content` is accepted as the final
answer.  Rapid DeepInfra mode is currently restricted to Qwen model IDs because
that is the model family for which the `<think>` prefill representation is known.
Larger quanta such as 64 or 128 are more sensible for a remote provider because
each quantum is a separate request.

## Selected options

```text
-a, --a-url URL          model A /v1/chat/completions URL
-b, --b-url URL          model B /v1/chat/completions URL
-A, --a-model NAME       model A alias
-B, --b-model NAME       model B alias
    --a-provider NAME    llama or deepinfra (default llama)
    --b-provider NAME    llama or deepinfra (default llama)
-s, --system TEXT        common system message
-p, --prompt TEXT        seed from the command line
-t, --temperature N      sampling temperature
-n, --max-tokens N       completion cap; final-answer cap in rapid mode
-H, --history MODE       split, shared-a, shared-b
-q, --rapid N            rapid reasoning quantum in tokens
-R, --rapid-budget N     rapid reasoning budget/model
-C, --crosstalk N        autonomous cross-feed rounds; -1 means unbounded
-d, --debug              show reasoning and rapid quanta
-P, --no-template-check  skip ordinary template validation
```

### Native reasoning delimiters

Rapid prompts are bracketed by model-specific delimiters discovered from
`/apply-template`: Twinception prefills the generation-to-reasoning prefix and
stops on the reasoning-to-answer transition.  llama-server excludes the matched
stop string from `content`.  Thus protocol syntax such as GPT-OSS Harmony's
`<|channel|>analysis<|message|>` opening prefix and final-channel transition never
becomes crossed reasoning payload.
