# twinception

Experimental C23 client for paired LLM inference.  The ordinary mode
crosses complete reasoning traces between turns.  Rapid mode goes further: the
models generate short reasoning quanta in lockstep, and each model's next
inference is conditioned on the *other* model's accumulated reasoning rather
than its own.

The program uses libcurl's multi-socket interface with epoll/timerfd; there are
no HTTP worker threads or polling loops.

The same machinery also drives [`askai`](#askai-an-ask-an-ai-mcp-server), an MCP
server that gives a model running in `llama-server` a tool for asking another AI.

## Dependencies

- C23 compiler
- libcurl
- json-c
- Linux epoll + timerfd

## Build

```sh
make            # builds twinception and askai
make check      # end-to-end tests of both, the dstr trials and check-load
make check-dstr # only the dstr trials
make check-load # only askai's load verdict on a light mix (10-20 s)
make load       # askai's load verdict on the storm (doc/core-measurements.md)
```

## Ordinary whole-turn swapping

Run two current llama.cpp `llama-server` instances on separate ports, then:

```sh
./twinception -d
```

Both receive each human prompt.  In the default `split` history mode, after a
completed turn:

```text
A history: answer_A + reasoning_B
B history: answer_B + reasoning_A
```

`-H shared-a` and `-H shared-b` instead force the visible assistant content in
both histories to come from one selected model while retaining crossed
reasoning.

Before inference, twinception uses `/apply-template` to verify that the
immediately preceding `reasoning_content` actually survives the model's chat
template.  If older historical reasoning is pruned it warns but continues.  A
template that drops the latest reasoning is rejected.  `-P` disables this check
for a non-llama proxy when its behavior has been verified separately.

## Causal rapid swapping

```sh
./twinception -q 32 -R 512 -n 2048 -d
```

`-q N` enables rapid mode and sets the maximum number of generated tokens per
reasoning quantum.  `-R N` caps the total rapid reasoning generated by each
model in one turn; it defaults to 512 when `-q` is present.  `-n` becomes the
final-answer token cap.

For each user turn, twinception first asks `/apply-template` for each local
llama.cpp model's native prompt.  At startup it has already compared a user-only generation prompt
with a synthetic completed assistant turn, so it knows both the model-specific
generation-to-reasoning prefix and the reasoning-to-answer transition.  It
replaces/prefills the former before using llama.cpp's raw `/completion` endpoint
with `cache_prompt=true`:

```text
round 0:  A sees base_A                 B sees base_B
           emits a0                      emits b0

round 1:  A sees base_A + b0            B sees base_B + a0
           emits a1                      emits b1

round 2:  A sees base_A + b0+b1         B sees base_B + a0+a1
           ...                           ...
```

A model's own emitted reasoning is never appended to its next prompt.  The
plain text is crossed; each destination server tokenizes it with its own
vocabulary.

Rapid mode therefore makes two startup `/apply-template` probes per model.  A
user-only render identifies the ordinary generation tail; a synthetic completed
assistant turn contains a reasoning sentinel followed by an answer sentinel.
Their differing tails identify the native reasoning-entry prefix, while the
bytes between the two sentinels identify the reasoning-to-answer transition.
This matters for Harmony/GPT-OSS: raw generation would otherwise begin with
`<|channel|>analysis<|message|>`, which is protocol syntax rather than reasoning
payload.  Twinception now prefills that syntax itself, so it is never crossed or
stored as thought.

After the rapid reasoning budget (or an early reasoning stop), the native
reasoning-to-answer transition is appended to each destination prompt and a
final `/completion` is requested.  Consequently rapid mode does not require old
reasoning traces to survive historical chat-template rendering, but it does
require llama.cpp-compatible `/apply-template` and `/completion` endpoints on
each local side.  `-P` is therefore invalid with `-q` when either provider is
llama.cpp; an all-DeepInfra rapid run has no template probe to skip.

Small quanta increase causal coupling but also increase HTTP/task scheduling
and prompt-suffix processing overhead.  `16` or `32` is a sensible first test;
`64` is a useful comparison point.  Use a dedicated server slot (`-np 1`) for
each model when measuring cache behavior.

## Crosstalk

`-C N` adds N autonomous rounds after each human/seed turn.  The visible answers
are crossed as the next user inputs:

```text
next A user <- previous B answer
next B user <- previous A answer
```

For example:

```sh
./twinception -C 20 -p 'You may now address the other participant.' -d
```

`-C -1` runs without a round limit.  `:stop` prevents another autonomous round
after the current pair finishes; `:quit` also exits once the in-flight pair has
completed.  `split` is the least confounded history mode for ordinary dialogue;
using `shared-a`/`shared-b` with crosstalk is allowed and intentionally produces
stranger autobiographical histories.

Rapid swapping and crosstalk can be combined:

```sh
./twinception -q 32 -R 512 -n 1024 -C 10 -d \
  -p 'You may now address the other participant.'
```

A paired turn is transactional in both modes.  If either backend fails, neither
history advances and autonomous crosstalk is stopped.

## DeepInfra

Either side can use DeepInfra instead of llama.cpp.  `Qwen/Qwen3.6-35B-A3B`
is the default hosted model.  Ordinary turns use DeepInfra's OpenAI-compatible
reasoning stream; crossed historical thought is replayed as
`reasoning_content`, with Qwen `preserve_thinking` explicitly enabled through
`chat_template_kwargs`.

Set the API key in the environment rather than putting it on the command line:

```sh
export DEEPINFRA_API_KEY='...'
```

`DEEPINFRA_TOKEN` is accepted as an alias because DeepInfra's documentation uses
both names in examples.

For two DeepInfra-hosted models:

```sh
./twinception --a-provider deepinfra --b-provider deepinfra -d
```

For one local llama.cpp model and one DeepInfra model:

```sh
./twinception --b-provider deepinfra -d
```

`-A`/`-B` override the DeepInfra model ID, and `-a`/`-b` can override the API
URL.  The default endpoint is
`https://api.deepinfra.com/v1/openai/chat/completions`.  DeepInfra automatically
caches repeated prompt prefixes, which is useful for rapid mode.

DeepInfra does not expose a documented raw reasoning-format extension.  Rapid mode
therefore uses the documented assistant-continuation behavior instead: it sets
`continue_final_message=true` and prefills a Qwen reasoning response with the
other model's accumulated trace.

```text
round 0:  assistant prefill = <think>\n
round 1:  assistant prefill = <think>\n + foreign quantum 0
...
answer:   assistant prefill = <think>\n + foreign trace + </think>\n
```

Thinking quanta stop on `</think>`.  DeepInfra may return the continued thought
as `delta.reasoning_content` or as raw `delta.content`; Twinception accepts both
for the thinking phase, but only ordinary `content` is accepted as the final
answer.  Rapid DeepInfra mode is currently restricted to Qwen model IDs because
that is the model family for which the `<think>` prefill representation is known.
Larger quanta such as 64 or 128 are more sensible for a remote provider because
each quantum is a separate request.

## Selected options

```text
-a, --a-url URL          model A /v1/chat/completions URL
-b, --b-url URL          model B /v1/chat/completions URL
-A, --a-model NAME       model A alias
-B, --b-model NAME       model B alias
    --a-provider NAME    llama or deepinfra (default llama)
    --b-provider NAME    llama or deepinfra (default llama)
-s, --system TEXT        common system message
-p, --prompt TEXT        seed from the command line
-t, --temperature N      sampling temperature
-n, --max-tokens N       completion cap; final-answer cap in rapid mode
-H, --history MODE       split, shared-a, shared-b
-q, --rapid N            rapid reasoning quantum in tokens
-R, --rapid-budget N     rapid reasoning budget/model
-C, --crosstalk N        autonomous cross-feed rounds; -1 means unbounded
-d, --debug              show reasoning and rapid quanta
-P, --no-template-check  skip ordinary template validation
```

### Native reasoning delimiters

Rapid prompts are bracketed by model-specific delimiters discovered from
`/apply-template`: Twinception prefills the generation-to-reasoning prefix and
stops on the reasoning-to-answer transition.  llama-server excludes the matched
stop string from `content`.  Thus protocol syntax such as GPT-OSS Harmony's
`<|channel|>analysis<|message|>` opening prefix and final-channel transition never
becomes crossed reasoning payload.

## askai: an "ask an AI" MCP server

`askai` is an [MCP](https://modelcontextprotocol.io) server whose tool,
`ask_ai`, forwards a prompt to another AI model and returns its answer.  A
small local model in `llama-server` can use it for a second opinion, or to hand
a hard sub-problem to a bigger model.  The other model sees only the prompt, so
the tool description asks the caller to make it self-contained.  With `--man`,
a second tool, `man`, reads the manual, and with `--git`, a tool `git` runs
read-only git commands in the repositories it lists (below).

It speaks MCP's Streamable HTTP transport, which is what the `llama-server` web
UI's MCP client uses, and serves both protocol eras on one endpoint:

- revisions 2024-11-05 through 2025-11-25, which open with an `initialize`
  handshake (current llama.cpp and the official SDKs);
- revision 2026-07-28, which is stateless and checks the mirrored
  `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` headers against the body.

A tool call answers on an event stream (SSE) when the client accepts
`text/event-stream` and its revision has them (all but 2024-11-05): the stream
opens as the call starts, carries a `:` comment every 15 s while the other
model works (`--sse-keepalive`), and ends with the result as one `data:`
event.  A call whose `params._meta` has a `progressToken` also gets
`notifications/progress` on its stream, at most one every 100 ms: its place in
its session's queue while it waits for the upstream, then the tokens of the
answer as they come, "thinking" while the latest is the model's thinking and
"generating" once it is the answer's text.  Other requests, and clients that accept only JSON, get
JSON.  Request bodies may come with a `Content-Length` or in chunks.

### Upstream protocols

| `-p`        | API                      | Default endpoint (without `-u`)                                                 | Key variable                       |
| ----------- | ------------------------ | ------------------------------------------------------------------------------- | ---------------------------------- |
| `openai`    | Chat Completions         | `https://api.openai.com/v1/chat/completions`                                    | `OPENAI_API_KEY`                   |
| `responses` | OpenAI Responses         | `https://api.openai.com/v1/responses`                                           | `OPENAI_API_KEY`                   |
| `anthropic` | Anthropic Messages       | `https://api.anthropic.com/v1/messages`                                         | `ANTHROPIC_API_KEY`                |
| `gemini`    | Gemini `streamGenerateContent` | `https://generativelanguage.googleapis.com/v1beta/models/MODEL:streamGenerateContent?alt=sse` | `GEMINI_API_KEY`, `GOOGLE_API_KEY` |

`openai` also covers every OpenAI-compatible server: another `llama-server`,
vLLM, Ollama, LM Studio, OpenRouter, Groq, DeepInfra and so on.  Reasoning or
thinking output is dropped; only the answer is returned.  An answer cut off by
the token limit is marked as such, and upstream failures (HTTP errors, error
events, refusals, timeouts) come back as tool errors the model can read and
react to.

Every protocol asks for a streamed answer: `stream: true` in the body, which
`-x` cannot turn off, and for Gemini `:streamGenerateContent?alt=sse`, which a
`-u` URL ending in `:generateContent` is asked as instead, with `alt=sse`
whatever `alt` it had.  The tool still
returns the whole answer at once; streaming lets `askai` report progress,
notice a stalled answer (`--chunk-timeout`, 60 s between chunks once it has
begun) and cancel generation upstream as soon as the client goes.  A server
that answers with plain JSON all the same is understood too.

API keys are read from the environment, never from the command line.  A
provider's usual variable is only used for its own endpoint: with `-u`, name the
variable explicitly with `-k`, so a key is never sent somewhere you did not ask
for.

```sh
# Ask an Anthropic model.
export ANTHROPIC_API_KEY=...
./askai -p anthropic -m MODEL

# Ask a model served by a second llama-server (no key needed).
./askai -u http://127.0.0.1:8081/v1/chat/completions

# Ask a model on OpenRouter.
export OPENROUTER_API_KEY=...
./askai -u https://openrouter.ai/api/v1/chat/completions -k OPENROUTER_API_KEY -m MODEL

# Ask a Gemini model.
export GEMINI_API_KEY=...
./askai -p gemini -m MODEL
```

`-x` deep-merges a JSON object into every request body, which reaches any
provider-specific parameter; `null` members delete keys.  For example, OpenAI
reasoning models want `max_completion_tokens` instead of `max_tokens`:

```sh
./askai -m MODEL -n 4096 -x '{"max_tokens": null, "max_completion_tokens": 4096}'
```

### Connecting llama-server

Start `askai`, then add `http://127.0.0.1:8090/mcp` as an MCP server in the
`llama-server` web UI.  The UI calls it straight from the browser, which `askai`
permits for pages served from `localhost`, `127.0.0.1` or `[::1]`.  If the UI is
served from another origin, either allow that origin with `-o`, or start
`llama-server` with `--ui-mcp-proxy` and enable the proxy for this server.

Each tool call is one upstream request; if the user stops generation, the
web UI sends `notifications/cancelled`, or closes the call's connection, and
`askai` aborts the upstream request.  `askai` asks the other `llama-server`'s
`/props` how many slots it has (`-np`), and makes as many upstream requests at
once; the rest wait their turn (`--slots` says how many instead).
The web UI waits five minutes for a tool result by default; `askai` lets a
call wait ten minutes for a slot and ten more for the upstream answer (`-T`).
Raise both for slow reasoning models.

Running several instances with different `--tool-name` values (and ports) gives
the model a choice of advisers, e.g. `ask_reasoner` and `ask_coder`.

### Reading the manual

With `--man`, `askai` also offers the tool `man`: a page of the manual of the
machine `askai` runs on, as `man [section] name` shows it, in UTF-8 text, so
that a model can check the interface of a system call, library function or
command rather than recall it.  Its arguments are the page's `name` and an
optional `section`, such as `2`, `3`, `3p` or `7`.  A name is 1 to 128
letters, digits and `_.:+@-`, and a section 1 to 16 letters and digits, neither
beginning with `-`, so neither can become an option or a path.

`askai` runs `man` itself, with no shell: `man -w -s SECTION -- NAME`, which
finds the page's file, then `man -l -- FILE`, which renders it.  Each runs in a
session of its own, its standard error discarded, with an environment of its
own: `PATH` and `MANPATH` as `askai` has them, `LC_ALL=C.UTF-8`, `MANWIDTH=80`,
and `MANROFFOPT='-rHY=0 -dAD=l'`, which turns hyphenation and justification
off, as a model reads words split across lines, or padded with spaces, less
well.  A page longer than 2 MiB is cut there with a note saying so; `gcc(1)`,
the longest page of many a system, renders to 1.4 MiB, which is some 370,000
tokens, more than many a model's context holds.

Each page is rendered once and kept, by its file: `printf` in section `3p` and
in `3posix` share one rendering, as do `S_ISBLK` and `inode(7)`, which the
former's file points to.  Asked for again, a page comes from memory, in 0.3 ms
for `pthread_create(3)` and 5.5 ms for `gcc(1)`, as long as its file is as it
was; a file that has changed is rendered anew.  A name `man` has found a file
for is found anew once that finding is ten minutes old, in the background,
the kept page given meanwhile, so that a page installed since, which `man`
would find first, takes over.  Calls for a page under way wait for its one
rendering.  Pages are kept for good: all of a system's pages take some 100 to
200 MiB.  `GET /metrics` shows the pages kept and their bytes, the calls a
kept page answered and those that waited, and the runs of `man`.

A missing page is a tool error, "No manual entry for NAME in section S.", and
so are `man`'s other failures and a page that takes more than 10 s to find or
render; none of those is kept.  At most 16 `man` and `git` processes run at
once; a call past those is answered as busy.  A call that goes, as when its client closes
the connection, leaves the page to be rendered and kept; stopping `askai`
kills `man` and the processes it started.

### Reading git repositories

With `--git PATH`, which may repeat, or a configuration file's `"git"` list,
`askai` also offers the tool `git`: read-only git commands in the repositories
listed, each a work tree's top or a git directory, and named by the last
component of its path as given, less a `.git` suffix: `/srv/git/proj.git` is
`proj`.  A name is 1 to 64 letters, digits and `_.-`, not beginning with a dot;
a path without one, or two of one name, are refused as `askai` starts.  A call names its
`repo` and its `command`, one of `log`, `show`, `diff`, `grep`, `blame`,
`ls-files`, `ls-tree`, `cat-file` and `rev-parse`, and gives its `options`, its
`revisions` and its `paths` apart, and for `grep` its `pattern`:

```json
{ "repo": "proj", "command": "log", "options": ["--oneline", "--max-count=20"],
  "revisions": ["main..topic"], "paths": ["src"] }
```

Each option must be one the command's allowlist has, its value attached
(`--max-count=20`, not `-n 20`); revisions follow `--end-of-options` (but for
the commands that take it amiss), and may not start with `-` or `/` nor have a
`..` component; paths follow `--`, relative to the repository's top, with no
`..` component; a pattern follows `-e`; `rev-parse` looks at revisions only.
So no option that writes a file (`--output`), reads one from outside the
repository (`grep -f`, `blame --contents`, `--no-index`) or runs a program
(`grep -O`, `--ext-diff`, `--textconv`) can come from a client.  `askai` runs
`git` itself, with no shell, in a session of its own, with an environment of its
own (`PATH` as `askai` has it, `LC_ALL=C.UTF-8`, a `HOME` that does not exist,
no system or global configuration, no terminal prompts, no optional locks, no
repository looked for above the listed ones, and no remote protocol or fetch of
a partial clone's missing objects) and with settings that stop what a
repository's configuration could have it run: no pager, fsmonitor, gpg (which a
log's format may ask for), hooks or submodule diff, and no refresh of the
index, and `safe.directory` for the repository, as listing it trusts it.  The rest of a
repository's own configuration, such as filters that a work tree's files pass
through, is trusted likewise: list only repositories whose configuration you
trust.

The reply is `git`'s output, its errors included, made UTF-8 text and cut at
2 MiB with a note saying so; an exit status other than 0 is noted, and is a
tool error but for 1 with nothing written, as `grep` finding none.  At the
deadline, `--git-timeout` (30 s), `git` gets SIGTERM, and SIGKILL a second
later, and the call is a tool error; a call that goes, or `askai` stopping,
kills `git` and the processes it started.

### Security

`askai` spends your API credits, so by default it listens on 127.0.0.1 only and
refuses browser requests whose `Origin` is neither loopback nor allowed by `-o`,
which defeats DNS-rebinding attacks.  Before listening anywhere else, set
`ASKAI_TOKEN`, or name identities in a configuration file (below); clients must
then send `Authorization: Bearer <token>`, which the web UI can add as a custom
header.  A Unix socket (`--listen unix:PATH`) knows its clients' users without
a token; its file's mode follows `askai`'s umask, and `askai` removes it as it
stops.  With `--git`, whoever may call the tool may read the repositories
listed.

### Configuration file, identities and roles

`--config FILE` (`-c`) reads options from a JSON object too, which may hold
comments: each member is named as a long option is, its value the option's
argument, a string or a number (`extra` may be an object); `true` for an option
that takes none; an array for one that repeats.  The command line overrides
the file: repeatable options add up, but for `listen`, which the command line's
replace.  Only root or `askai`'s user may change the file or any directory
above it (others may add to a sticky one, such as `/tmp`), and it must be a
regular file, not a symbolic link.

Four more members say who may connect, and what they may do:

```json
{
  "url": "http://127.0.0.1:8081/v1/chat/completions",
  "man": true,
  "listen": ["127.0.0.1:8090", "unix:/run/askai/askai.sock"],
  "roles": {
    "admin":  { "tools": ["ask_ai", "man"], "metrics": true },
    "user":   { "tools": ["ask_ai", "man"] },
    "reader": { "tools": ["man"] }
  },
  "identities": {
    "alice": { "role": "admin", "unix-users": ["alice"],
               "tokens": ["sha256:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"] },
    "ci":    { "role": "user", "tokens": ["env:ASKAI_CI_TOKEN"] }
  },
  "unix-groups": { "developers": "user" },
  "anonymous": { "loopback": "reader", "remote": null, "unix": null }
}
```

- A **role** lists the tools it may list and call, as clients see them
  (`--tool-name`'s, `man` and `git`), and whether it may read `GET /metrics`.
  `tools/list` shows a client its role's tools only, and calling another is
  an error, "Tool not available: NAME".
- An **identity** has a role, and proves itself with a bearer token,
  `Authorization: Bearer TOKEN`: `"sha256:HEX"`, the token's SHA-256 digest
  (`printf %s TOKEN | sha256sum`), keeps the token out of the file, and
  `"env:NAME"` reads it from `askai`'s environment.  A client of a Unix
  socket is the identity whose `unix-users` (names or uids) holds its user,
  as the kernel says (`SO_PEERCRED`); a token, if it shows one, counts first.
- **`unix-groups`** gives the other users of a Unix socket the role of the
  first of their groups it names, among the groups they had as they
  connected (`SO_PEERGROUPS`).
- **`anonymous`** names the role of a client that shows no token: `loopback`,
  one on loopback that names it as `localhost`, `127.0.0.1` or `[::1]`;
  `remote`, any other over TCP; `unix`, a user of a Unix socket that no
  identity or group names.  `null`, as leaving it out, refuses them.

A token that no identity has is refused with 401, on the request's head
before its body, as is a client without one that no role is named for.  An
identity's calls are one principal of the scheduler's, whichever of its tokens
they show, and each other user of a Unix socket is one; anonymous TCP clients
are their sessions or addresses, as before.  User and group names are looked
up as the file is read, which with a directory service such as SSSD may wait
on it.  Without those four members, `askai`'s own policy holds: with
`ASKAI_TOKEN` set, clients must show it and may do everything; else clients on
loopback that name it so, or on a Unix socket, may do everything, and others
may call the tools.  With them, `ASKAI_TOKEN` is ignored, as `askai` notes.

With `--config`, SIGHUP reloads who may connect and what they may do: a
blocker thread reads the command line and the file again, and the new policy
takes over for the requests that begin from then on, while those under way
finish as they began.  A file that is wrong is logged, and the last policy
stays; the other options take a restart, as the log says when they changed.
Without `--config`, SIGHUP stops `askai`, as SIGTERM does.

### Limits

`askai` bounds what each client may send and hold, so that slow, oversized or
abusive clients cannot tie up its event loop, its memory or its descriptors.
Every limit is an option (see below); a breach gets the HTTP status a client
can act on:

| Limit | Default | Breach |
| ----- | ------- | ------ |
| request line and headers | 16 KiB, 64 fields, sent within 10 s | 431, 408 |
| request body | 1 MiB, averaging at least 4 KiB/s after 5 s | 413, 408 |
| JSON in a body | 32 levels deep, 1024 values, 1024 members in an object, numbers of 1 KiB | 400 |
| bodies held for all clients | 256 MiB | 503 |
| bodies held for one client address | a quarter of those | 503 |
| connections per client address (IPv4, or IPv6 /64) | 256 | 503 |
| idle keep-alive | 30 s | close |
| pending output | 256 KiB holds requests back, 1 MiB unless one response is all of it | close |
| output stalled | 30 s | close |

The limits hold for the whole process, whichever event loop serves a client.
Bytes trickling in or out never extend a deadline.  When `askai` ends a
connection, it half-closes it and discards what the client still sends for up
to 2 s, so that a client that sent too much still reads the error.  With
`ASKAI_TOKEN` set, a request without the token is refused before its body.
Raise `--max-body` (and `--body-budget`) to pass large documents to the other
model.  Bodies and answers are parsed and freed, prompts and answers passed
on, and replies sent, a slice at a time, so a large one hardly holds up other
clients: only copying its longest string takes a single step, of about 0.4 ms
per MiB, as does copying an answer's text (answers may take up to 16 MiB).
Raising `--max-values` lets a body hold more values, each of which json-c
holds in up to 0.7 KiB while the request runs.

`askai` keeps the memory its work has used for the work to come: buffers go
back to a stash of the event loop and come out of it again, up to twice the
most they held at once, and finished requests are kept for reuse too, so a
steady load allocates none.  It gives memory back to the system only under
memory pressure: resident memory over `--memory-high` (by default a sixteenth
of RAM, or of the lowest cgroup limit, at least 256 MiB), RAM or a cgroup's
limit nearly used up (file cache the kernel can reclaim aside), or the
kernel's pressure stall information.  It then frees what went unused for
10 s or more, or under critical pressure all it keeps, a slice at a time, and
the allocator returns what is free to the system in one call that takes about
55 µs per MB.

Sending `askai` SIGUSR1 prints statistics of its event loops since the
previous SIGUSR1, each loop's in lines that name it (`loop1` to `loopN`, and
`home`): how long their turns and steps took, how late their timers fired,
and the most work of each kind a step did against its bound.

### Running

`askai` serves clients on event loop threads, by default one fewer than the
CPUs it may use, as its affinity and its cgroup's CPU quota allow (`--loops`),
and asks the other model from another, home.  Home accepts the clients and
places each on the lighter of two client loops, by the connections they hold
and how busy they are; the client stays with that loop.  A tool call hands its
upstream request to home as a job, which home runs and hands back.  Home makes
as many upstream requests at once as the upstream has slots (`--slots`; by
default what `llama-server`'s `/props` says for every protocol but `gemini`,
else 4).  The other calls wait, each in its principal's queue, its client's
identity's, else its MCP session's or, without one, its client address's,
and the principals take
turns, a call each, so that one flooding client leaves the others their share.
At most `--max-calls` (256) are under way, and eight queued for one principal
(a call that a free slot takes at once waits in no queue); a tool call past
those is answered at once with a tool error that says to try again.  A client that goes while its call waits or
runs cancels it, upstream too, as does a `notifications/cancelled` for it that
comes on any connection.  After five upstream failures in a row (connection
errors, timeouts, HTTP 5xx and 429), or an answer's `Retry-After`, tool calls
are refused at once, saying when to try again: for a second, or as long as
`Retry-After` asked.  Then one call probes the upstream, and the wait doubles,
up to a minute, until one goes through: as soon as its answer begins, the
others go too.
The main thread minds signals, the process's memory and descriptors (and the
kernel's pressure stall information where there is some), and a watchdog that
logs a loop turn longer than 20 ms (`--watchdog`).  A logger thread alone
writes stderr: a reader of stderr that stops reading holds up no client, as
lines that do not fit in its buffers are dropped and counted.  Two more
threads look up the upstream host, so libcurl starts no threads of its own.

`GET /metrics` returns metrics in Prometheus's text format: each loop's turn
and step times, timer lateness and inbox delay (`loop="1"` to `loop="N"`, and
`loop="home"`), each client loop's request times by MCP method and its
connections, home's jobs, its queue, slots and breaker, streamed answers'
chunks, upstream wait and run times, host lookups, log lines dropped,
watchdog reports, memory and descriptors, memory pressure and its inputs, and
what the loops keep for reuse and gave back.
It answers the clients whose role may read it: without a configuration file
that says otherwise, those on loopback that name it as `localhost`,
`127.0.0.1` or `[::1]` (or send no `Host`), or on a Unix socket, and with
`ASKAI_TOKEN` set, those that send the token.

The first SIGINT or SIGTERM, or SIGHUP without `--config`, makes `askai` drain: it stops accepting
clients, closes idle connections, answers tool calls that wait for the other
model with an error (on an event stream, as its last event), finishes other
requests, and exits 0, all within a grace period of 5 s (`--grace`).  A second
signal, the grace period running out, or an event loop stuck in one turn for
a second ends it at once, with exit status 3.  A signal that `askai` started
with ignored, as under `nohup` or in a shell's background job, stays ignored.
Invalid options or environment exit 2, and a failure to start or to serve 1.

## dstr

Strings are handled with `dstr` ([`src/dstr.h`](src/dstr.h)), a dynamic string
with Short String Optimization.  A `struct dstr` is a value, not a handle: a
string that fits in the object (23 bytes on 64-bit targets by default) lives in
place, and a longer one in a heap buffer allocated in 256-byte blocks, which is
wiped before it is freed.  An all-zero object is *not* an empty string;
initialize every object with `dstr()` or `DSTR_INIT`.

A `dstr` holds UTF-8 text only; anything in another encoding is converted at
the boundary before it goes in (the library doesn't validate this yet).  The
null character U+0000 is valid UTF-8, and since a `dstr` keeps its own length,
its content may contain nulls: `dstr_len()` counts every byte, while
`dstr_get()` read as a C string stops at the first null.

The object size can be chosen per translation unit by defining `DSTR_OBJ_SIZE`
(a multiple of `sizeof (uintptr_t)`, from `3 * sizeof (uintptr_t)` to 128)
before including `dstr.h`.  The library functions in `dstr.c` take the object
size at run time, so translation units that use different sizes link against
the same `dstr.c.o`.

The test trials live in [`tests/dstr`](tests/dstr): API contracts, a boundary
sweep and a randomized model check at every legal object size, allocation
failure injection, header hygiene, big-endian and 32-bit targets under
qemu-user, and constant folding of short literals.

```sh
tests/dstr/run.sh                        # every trial, with clang and gcc
tests/dstr/run.sh -l 03 -t gcc -S address,undefined
tests/dstr/run.sh -h                     # all options
```
